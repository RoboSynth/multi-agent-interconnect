## 失败、修复与保留记录

1. PowerShell / Windows C 程序的中文路径并不等价。直接中文 Nginx 前缀报 1113 字符转换错误；Temp junction 前缀报 CreateFile 访问拒绝。改用项目内实际文件的会话 DOS 驱动映射后，Nginx `-t` 与实际入口就绪均通过。
2. 沙箱内 `pg_ctl start` 再次创建 restricted token 失败。`business/native_postgres.py` 使用当前受限令牌直接启动指定项目 PostgreSQL，并等待 `pg_isready`；不提权、不把失败当成功。
3. Python 子进程调用 PowerShell WMI `Get-CimInstance` 被拒绝（0x80041003）。改为 `business/native_process.py`：持有 OS 进程句柄、查询真实命令行、确认项目脚本 / 版本后终止同一句柄，避免 PID 复用误杀。旧失败保存为 `business-native-acceptance-wmi-failure.json`。
4. Nginx 的 reload 信号命令成功早于新 worker 实际接管。初轮 F02 请求过早，仍命中 v2，结果明确失败并保存在 `business-native-acceptance.json`。现恢复 primitive 用新连接确认公共 `/health` 的实际版本；F12 同时确认标准 Via 中继链路后再停回复代理。F02 / F12 仅重跑受影响场景，成功结果另存 `business-native-acceptance-route-fix.json`。
5. F12 初轮在路由信号返回后过早停止代理，后续同键重试发生 `httpx.ReadError`；同一异步路由修复后，完整提交→超时→回执→同键重试与 30 秒观察通过。初轮未完成的 F12 不计入成功次数。
6. 注入器创建原生子进程的环境改为系统变量白名单，再显式传入所需本域变量。应用只拿应用账号和管理 token；回复代理不拿数据库或应用凭据。运维域重启后使用其过滤后的应用启动环境。
7. 代码对接审查发现，验证方若同事故反复使用同一负载 namespace，会重放旧订单回执。现 namespace 包含 incident_id 和 logical_task_id，后一次验证会使用新业务键；轻量边界回归 `tests/business_verification_test.py` 已通过，不修改目标业务。
