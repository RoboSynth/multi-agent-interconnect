## P1 平台访问量

### 现象

- 平台公开文档（https://wt.ioa.pub/docs.html，10-19 核对）已写明外部 Agent 上报端点为 `wt.ioa.pub:19092`，Kafka PLAINTEXT，不需要账号或证书。统计口径原文是：“统计 access 日志，correlationId 填写为 taskId，按照 taskId 双方匹配作为 1 次调用/被调用”。Message 日志也可计数，要求 `correlationId`=taskId、收发两端 `messageId` 相同、`eventType` 包含 send 和 receive。
- 团队已在 `docs/kafka_接入一页纸.md` 中准备好公开配置和离线预检，但**还没有真实发送过**，记录写的是“待获准后发送”。
- 官方源码中，按 AIC 计数的唯一来源就是 Kafka `amp.access`（`monitor-server/app/access/store.py:143-179, 345-388`）。broker 流量、群组 ACL、发现查询都不计数。**不发送日志，排名一定是 0。**

### 根因与核对结果

1. **access 日志的关联字段符合口径（确定）。** `vendor/ACPs-community/acps-sdk/acps_sdk/amp/group_access.py:105-106` 写的是 `correlation_id=taskId`，Leader 发送端（`aip_group_leader.py:929-930`）和 Partner 接收端（`aip_group_partner.py:974-975`）都写，caller/callee 为双方 AIC，只在 Start 时记一条。能够按 taskId 配对。
2. **message 日志的关联字段不符合口径（确定）。** Leader 和 Partner 的 message 打点全部使用 `correlation_id=body.get("sessionId")`（`aip_group_leader.py:475, 512, 540, 879`；`aip_group_partner.py:800, 821, 845, 1122`）。平台若按 message 统计任务次数，这些日志无法按 taskId 配对。这是官方 SDK 与平台口径之间的不一致。
3. **调用方只 @ 一个参与者时，Leader 端的 callee 才是具体 AIC（确定）。** 多个 mention 时会写成 `group:<groupId>`（`group_access.py:63-64, 90-91`），这样就无法配对。本项目每个任务只 @ 一个参与者，目前没有问题，但要在代码里加断言，防止以后改动破坏配对。

### 解决方案

| 步骤 | 内容 | 位置 |
| --- | --- | --- |
| 1 | 按一页纸接通七个来源的 Fluent Bit → `wt.ioa.pub:19092`，先只发新日志（`Read_From_Head False`） | `deploy/fluent-bit/` |
| 2 | **自检方法：** heartbeat 送达后，Discovery 响应中本队 AIC 的 `aliveMap` 会变为在线。这是不需要管理员权限就能确认“Kafka 入库链路通了”的方法。发送后 2 分钟内查询七个 AIC | 新增 `tools/check_alive.py` |
| 3 | message 打点改为：task 命令和 task 结果消息用 `taskId` 作 `correlation_id`，其他管理消息保留 `sessionId`。8 处调用点统一改成一个辅助函数 `_message_correlation(body)` | `aip_group_leader.py`、`aip_group_partner.py`（fork 内改，另提 Issue 说明 SDK 与平台口径不一致） |
| 4 | `GroupAccessMiddleware` 在 `direction="send"` 且 mention 数不为 1 时打 warning，并在测试中断言本项目的 access 全部可配对 | `group_access.py` + 测试 |
| 5 | 本地对账脚本 `eval/reconcile_access.py` 增加“按平台口径配对”的输出：同一 taskId 两端各一条才算 1 次 | `eval/reconcile_access.py` |

**验收：** 七个 AIC 在 Discovery `aliveMap` 中在线；本地按平台口径配对率为 100%（不含实验崩溃例）；请平台管理员确认 `amp.access` 主题收到本队记录（这一步需要人去问）。

**需要用户决定：** 是否把历史真实运行的 access 日志补发一次（E3、健康窗口、平台验收等，都是真实发生过的任务）。补发的好处是排名基数更高；风险是旧日志中有 11 条坏行和缺端记录，平台口径对旧时间戳是否计入也不清楚。建议：只补发能按 taskId 两端配对的记录，并先问平台管理员是否接受历史时间戳。

## P2 长期巡检

### 现象与根因（确定）

- 8877 巡检于 10-18 12:42:18Z 收到 `stop_when_idle`，正常关闭（`incident-pilot/artifacts/new7-inspect-session-20261018/runs/.../stop-request.json`、`finished.json`）；12:47Z 项目整体按用户要求暂停（`artifacts/project-shutdown-20261018/final-shutdown-verification.json`），WSL 保持进程也一起停了。**之后没有恢复。**
- 从未注册自启：`docs/windows_startup.md` 写明“未注册真实任务”。即使注册，现有任务也只启动调度器，不会启动 WSL、Docker、各个资源域和工作台（`ops/schedule.py:104-187` 只是通过 HTTP 调用工作台）。
- 巡检和实验无法共存：工作台持有协调者 AIC 的 Inbox，同一 AIC 只能有一个消费者，同一参与者也只能有一个活跃群组。`ScheduleLock`（`ops/schedule.py:34`）只锁调度器自己的状态目录，管不到实验对身份的占用。

### 解决方案

1. **身份租约（解决共存）。** 新增 `ops/aic_lease.py`：按 AIC 加文件锁，记录持有者、开始时间、用途。巡检每轮开始前获取七个身份的租约，结束后释放；实验运行器开始前获取租约，拿不到就等待；拿到后先调用巡检的 `stop_when_idle`，实验结束后释放并自动恢复巡检。所有暂停时段写入 `longrun` 记录，作为统计里的“计划内中断”。这比再申请一套实验身份简单，而且代码冻结后实验很少。
2. **开机自启三件套。** 三个任务计划，均为登录后运行，XML 加 `RestartOnFailure`（现有 `ops/install_startup.ps1:53-55` 没有）：
   - 第一个：启动 WSL 保持进程，执行 `docker compose up -d`（容器设 `restart: unless-stopped`）；
   - 第二个：延迟 60 秒启动 `workbench_server.py --port 8877`，先做健康检查；
   - 第三个：现有 `install_startup.ps1 -Register`，启动巡检调度。
   
   同时关闭睡眠，开启 Windows 自动登录。
3. **巡检频率。** 当前每 30 分钟一轮，每轮 12 个任务，每天约 576 次调用。运维健康检查每 5–10 分钟一次是常见做法，建议改为每 10 分钟一轮（约 1700 次/天），既真实又能提高排名基数。巡检本身会创建和取消测试订单，不对外产生影响。不建议加空转任务。
4. **状态脚本。** `ops/longrun_status.py` 已能统计外部调用次数，补充：连续在线时长、各 AIC 心跳覆盖率、本地可配对 access 数、最近一次中断原因。每天定时存一份快照。

**验收：** 重启电脑后无人工操作，10 分钟内七个身份恢复在线、巡检恢复；一个完整的 24 小时窗口；实验期间巡检自动暂停并恢复，记录完整。

## P3 平台调用缺少容错（批次失败的主要原因）

### 现象

- access 复验批次：after_observation 在建组时 `ConnectTimeout`；before_modification 在邀请时 `ConnectError`，关组也 `ConnectError`；之后的用例因清理守卫抛异常而未执行（`evidence/access-validation-results-20261019/README.md`）。
- 22 例批次首例 TimeoutError、关组 ConnectError（`evidence/platform-acceptance-20261019/summary.json`）；12 例复验中 full_history-r1 在接管时重新发现报 ConnectError。
- F10 成功的用例走的是同一条代码路径（`eval/run.py:59` 同样用 WutongTransport），所以是一次性网络失败没有容错，不是某个分支的缺陷。

### 根因（确定，代理部分为推测）

1. **群组 ACL 调用没有重试，异常也不包装。** 建组 `aip_group_leader.py:1767`、Inbox 邀请 `:1980` 都调用 `GroupAclClient.add_member`（HTTPS 到 9007）。`aip_group_auth.py:26-30` 只设了 `timeout=10`；`:68-87` 只把 HTTP ≥400 转成 `GroupAclError`，`httpx.RequestError` 直接抛出，没有重试。整个 SDK 只有 RPC 邀请有 3 次重试（`:649-698`）。
2. **关组失败会跳过资源清理。** 回滚（`:1789`、`:2024`）和关组（`:2391`）只捕获 `GroupAclError`；`ConnectError` 穿出后，`dissolve_group_session` 跳过 `:2397` 的 `cleanup_group_resources`，而会话已在 `:2371` 移除，exchange 和 queue 残留。
3. **发现调用没有重试。** `incident/selection.py:17` 只设 `timeout=25`；接管时的发现调用在候选循环的 try 之外（`incident/wutong_transport.py:343`），一次 `ConnectError` 就让整个接管失败。
4. **代理（推测）。** 项目自己的 httpx 客户端都设了 `trust_env=False`，只有 SDK 的 ACL 客户端和发现调用没设。协调者跑在 Windows 主机上，开着系统代理时 9007 的流量可能绕道代理，导致间歇性超时。
5. **批次在第一次关组失败后整体停止。** `run_authorized.py:141-147` 把任何 `close_error_class` 都判为不安全，`:196-197` 抛 RuntimeError，`:283-289` 循环终止，而且这个用例的回执也没写进汇总结果。

### 解决方案

| 改动 | 位置 |
| --- | --- |
| `GroupAclClient._request`：`httpx.Timeout(connect=5, read=10, write=10, pool=5)`；`trust_env=False`（需要代理时显式配置）；对 `ConnectError`、`ConnectTimeout`、`ReadTimeout` 和 5xx 做 4 次指数退避加抖动（0.5/1/2/4 秒）。PUT 加成员本身幂等；DELETE 返回 404 视为成功。其余 `RequestError` 统一包成 `GroupAclError` | fork 中的 `aip_group_auth.py` |
| `dissolve_group_session`：ACL 删除失败时记 warning，**照常执行** `cleanup_group_resources`，最后再抛出聚合错误 | `aip_group_leader.py` |
| 建组和邀请的回滚路径同样捕获 `RequestError` | `aip_group_leader.py:1789, 2024` |
| 发现调用设 `trust_env=False`，加同样的重试；接管路径中的发现放进可重试块；`wutong_transport.py:136` 的 `wait_for(…, 30)` 放宽到 60 秒 | `incident/selection.py`、`incident/wutong_transport.py` |
| 批次执行器：在 `finally` 中先把回执写入汇总，再判断能否继续；关组失败时先执行一次幂等的自有群组清理，再重新判断；如果只是关组网络错误，而资源恢复和 H00 都通过，就把这个群组名记入隔离清单并继续下一例 | `run_authorized.py` |

这几项同时是一个好的上游贡献：官方 SDK 在网络抖动下会残留 exchange 和 queue，可以作为第三个 PR 提交。

**验收（离线）：** 用 `httpx.MockTransport` 让前两次抛 `ConnectTimeout`、第三次返回 200，断言成功且调用 3 次；DELETE 抛 `ConnectError` 时 `cleanup_group_resources` 仍被调用；用桩结果让第 2 例产生 `close_error_class`，断言第 3 例仍会执行且回执进入汇总。**验收（平台）：** 合并 P3 后重跑那一批 4 例（F10 + 三个中断点），不再因为单次连接错误失败。

## P4 接管实验遗留

### full_history 失败（根因确定，已修复）

22 例批次中 full_history 3 次全败，表面错误都是 `TimeoutError`。真实原因是：生产端 `eval/resume_support.py:220` 给每条历史记录加了 `aip_session_id`，而冻结版 `acps_mcp_bridge/bridge.py:106` 要求字段集合严格等于 `{direction, aip_task_id, body}`，多一个字段就拒绝。拒绝时 `operation=None`，旧代码 `control.get("operation", {}).get(...)` 触发 `AttributeError`，`:239-241` 又用 `raise exc from takeover_error` 把它盖成最早的 `TimeoutError`。

提交 `2b4e28b` 已修正白名单并保留拒绝原因；复验 12 例中 full_history 的剩余 1 次失败属于 P3 的连接错误。**还需补两点：** 历史条目字段定义抽成生产端和 Bridge 共用的常量；`call()` 的结果中写入 `takeover_error_class` 和拒绝原因，不再只报最早的超时。补一个契约测试：用 `formal_semantic_history` 的真实输出直接喂给 `_handover_digest`。

### 每例缺 1 条 access（根因确定，离线已修，平台未复验）

18 条缺失全部在**接收端**，都是协调者发出的 Start：17 条是主数据库对被中断请求的记录，1 条是首例环境失败时的 verification。原因：`GroupAccessMiddleware.run` 只在 `finally` 中写 access，而实验用的退出钩子是 `exit_callback=os._exit`（`acps_mcp_bridge/experiment.py:140`），进程直接退出，`finally` 不会执行。

提交 `613ecbf` 的 durable access 针对的正是这一条：处理 Start 前先持久化意图（`group_access.py:61-70`），重启后写出一条 `OutcomeUnconfirmed`，`correlation_id` 相同，可以配对。它还没在平台上被验证，因为修复后的那批 E1 在到达中断点之前就因 P3 的网络问题失败了。

**这一项只影响崩溃实验，不影响日常巡检的访问量。** 处理方式：P3 合并后重跑那一批 4 例，一次性验证 T05。

## P5 创新三：证据驱动调度没有体现价值

### 现象

E3 正式结果（`evidence/new7-e3-45-20261018-first/`）和离线统计（`evidence/innovation3-heldout-20261019/offline-comparison.md`）：

| 方法 | 恢复 | 诊断正确 | 观察总数 | 修改尝试 | 无关修改 | 耗时中位数 | token |
| --- | --- | --- | --- | --- | --- | --- | --- |
| M0 固定观察顺序 | 15/15 | 15/15 | 108 | 24 | 0 | 42.7 秒 | 0 |
| M1 模型自由选工具 | 7/15 | 3/15 | 20 | 132 | 47 | 43.6 秒 | 51.2 万 |
| M2 证据排序 | 15/15 | 15/15 | 99 | 24 | 0 | 86.9 秒 | 13.6 万 |

M2 总耗时中，模型请求占 623.7 秒（47%），观察任务 145.5 秒，修改 36.6 秒，30 秒业务验证 518.5 秒。

### 根因（均确定，有代码位置）

1. **每一步都串行调用一次模型。** `incident/coordinator/engine.py:325-328`：每次选下一个探测前都调用 `hypothesis.generate()` 并等待结果，平均每例约 7.6 次，每次约 5.5 秒。模型只用来给最多 5 个探测排序，而一次观察本身只要约 1.5 秒。**模型调用的耗时比它可能省下的观察还多，所以 M2 在结构上不可能比 M0 快。**
2. **探测没有停止条件，M2 实际上也查遍了所有探测。** `planner.py:61-72` 的 `rank_probes` 会为每个剩余探测返回一行，区分度为 0 的也照样返回；`next_probe`（`:136-146`）只要列表非空就取第一个。只有 5 个探测全部观察完才返回 None。另外，“健康或其他”假设（`hypothesis.py:74-76`）对所有探测都有预测，总能与其他假设区分开，进一步保证每个探测都会被选到。这就是 M2 观察数（99）和 M0（108）几乎一样的原因。原设计文档写了“所有探测区分度为零时……没有有用探测……转人工或结案”，实现里漏掉了。
3. **M0 不是真正的固定剧本。** `eval/methods/__init__.py:6-15` 的 `FixedPlanner` 继承 `EvidencePlanner`，只改了观察顺序，修改动作仍由同一个 `actions()` 按证据决定。所以 E3 实际比较的是“有没有模型来排序”，而不是“证据驱动 vs 固定流程”。证据驱动的修改规划在 M0 和 M2 中都存在，两者的 0 次无关修改正说明了这一点，但这个价值在现有对比中没有对照组。
4. **问题空间太小。** 只有 5 个探测、4 种原因，每个探测都便宜，全部查一遍也只要约 7.5 秒。排序要有价值，探测必须“贵”。在跨组织场景中，真正的成本是“去打扰另一个组织”和“读取对方的敏感信息”（例如数据库会话和 SQL 内容），而不是秒数。

### 解决方案

**S1 去掉模型的串行等待（必做，预计 M2 耗时降到与 M0 接近）**

- 每个事故只在开始时调用一次模型生成假设；之后只有当新证据把全部候选假设都否定（`planner.candidates()` 为空）时，才再调用一次。用现有 `skip_deterministic_model_calls` 的思路扩展，而不是每步调用。
- 模型请求与入口探测并发：`entry_first` 规定前两个探测必定是 `ops.containers` 和 `ops.route_status`，它们不依赖模型结果，在等待模型时就并行发出。
- 互相独立的观察最多 3 个并行发出（方案原本允许），同资源修改仍串行。

改动位置：`engine.py:280-344` 主循环、`hypothesis.py` 增加“是否需要重新生成”的判断。

**S2 加停止条件（必做，让 M2 真正少查）**

- `next_probe`：若排序第一的探测区分度为 0，且当前没有需要补齐的前置事实（`required_probe` 为 None），返回 None，转入修改或验证。
- 修改完成后，先做一次快速症状复查（应用可达性观察加 3 个业务请求，约 3 秒），而不是直接进入 30 秒业务窗口；复查失败再重新生成假设。复合故障（F10）由这一步继续推进。
- “健康或其他”假设只在没有任何故障证据时保留，有确认原因后从候选集中移除。

改动位置：`planner.py:136-146`、`engine.py` 中修改后的流程。

**S3 加真正的对照组：盲修剧本（必做，体现证据驱动修改的价值）**

新增方法 MR：按症状查表执行固定修复脚本，不看证据。502 时依次重启应用容器、回退路由；写失败时依次恢复读写、结束阻塞会话、重建连接池。这就是很多团队手写的 runbook。在现有 5 个场景上，MR 会执行大量与原因无关的高风险操作（例如应用正常运行时也重启容器、数据库并非只读时也执行恢复读写），而 M0/M2 都是 0。这一组对比直接证明“只在证据支持时修改”的价值，属于创新三的核心。可以先在本地原生环境跑（不占平台身份），每场景 3 次，共 15 次。

**S4 用“跨组织调用”作为探测成本（推荐，体现排序的价值）**

把 `Probe.cost` 从“秒数”改为跨组织成本：调用其他组织的智能体记 1；读取敏感数据的探测（`db.blocking_sessions` 会返回其他组织的会话和 SQL）记 2，并在报告中解释为需要对方额外授权。新增指标“每例打扰的组织数”和“敏感观察次数”。S2 生效后，F01、F02 这类入口故障不再需要去问数据库方，M2 在这两个指标上会明显少于 M0。这正好对应作品“凭据不出域、跨组织”的定位。

**S5 剧本外故障（可选，时间够再做）**

用 1.7B 小模型扩展规则库之外的原因，成功率不确定。如果做，只测“诊断是否正确、是否正确转人工”，不要求自动修复。

### 改完后的对比实验

| 方法 | 说明 |
| --- | --- |
| MR 盲修剧本 | 新增，按症状执行固定修复 |
| M0 固定观察顺序 | 原 M0，改名以免误解 |
| M1 模型自由选工具 | 沿用 E3 结果 |
| M2v2 证据排序 | S1 + S2 + S4 |

先在本地原生环境跑 5 场景 × 4 方法 × 3 次，确认结论后，再决定是否上平台跑 M2v2（15 次）。旧 E3 结果保持不变，作为第一版数据。

**预期能写进报告的结论：** 证据驱动规划让无关高风险修改从 MR 的 X 次降到 0；停止条件让每例打扰的组织数比全量观察少 X%；模型只调用 1–2 次，耗时与固定顺序相近；对比模型自由调用，恢复率 15/15 对 7/15，token 减少 73%。

**验收：** 离线单元测试覆盖停止条件和“只调用一次模型”；本地 60 次运行结果和图；M2v2 中位耗时不超过 M0 的 1.3 倍。

## P6 体检智能体对外开放

### 根因（确定）

`domains/onboarding/check.py` 只读取目标 AIC 在 Discovery 上的公开 ACS，检查 schema、协议版本 02.02、AMQPS 端点格式和 skills 字段（`:44-86`），是安全的只读服务。代码支持对外（`public_metadata_service`，`check.py:38-41`，`incident/platform_worker.py:153-154, 245`），但默认是 False，两个配置生成脚本都不写入（`deploy/prepare_agents.py:92-96`、`domains/setup_platform.py:135-136`），`allowed_leaders` 只填本队协调者。外部调用会在邀请阶段被拒（“Leader is not authorized”），任务阶段返回 `caller_not_allowed`。

### 解决方案

1. `prepare_agents.py` 增加 `--public-onboarding` 参数，写入 `"public_metadata_service": true`；部署时带 `--include-onboarding`。
2. 体检智能体纳入长期巡检的租约和自启，保持在线和心跳。
3. 写一页对外调用说明和一个最小调用脚本：调用方自己当 Leader，经 ADP 找到并邀请体检智能体，发送 `observe` 任务，参数为 `aip.onboarding.check` 和 `{"target_aic": "...", "deep": false}`。
4. 被调用时 access 已按 taskId 写两端（P1），送进 Kafka 后计入双方的调用次数。

**验收：** 用一个非白名单的本队身份模拟外部调用并成功；`longrun_status` 的外部调用数增加。
