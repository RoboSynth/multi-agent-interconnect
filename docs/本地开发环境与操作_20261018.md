# 本地开发环境与操作（xiaomuxia 接手）

先在自己的电脑、自己的 GitHub 账号和新克隆目录开发。下面主线是**离线代码开发 → 独立四业务 → 业务验收 → 保留数据停机**，不要求平台身份、证书、模型或云主机。本文提供操作命令；本次整理没有恢复原开发机已停止的服务。

源码核对基线为 `8a820e419cea55f14d4de0edec76c0e1bcf87904`。克隆后记录自己的实际 HEAD；[队友部署记录](../deploy-check-record.md)固定的是更早的 `f689dae`，不能当成本文版本的全部测试结果。

## 4. Windows：独立四业务

Docker Desktop 已由自己正常开启且处于 Linux containers 后，确认工具可用、目标端口没有占用：

```powershell
docker version
docker compose version
Get-NetTCPConnection -State Listen -LocalPort 58081,58082,58088,58090 -ErrorAction SilentlyContinue
```

有占用就选择四个不同的新端口，统一修改**下一条 prepare 命令**；不要停止陌生进程。生成目录必须是仓库内的新空目录，project 名也要独占。以下固定使用 `incident-pilot-xiaomuxia-dev`：

```powershell
.\.venv\Scripts\python.exe deploy/prepare_deployment.py --mode business --output runtime/private/xiaomuxia-dev --project incident-pilot-xiaomuxia-dev --app-v1-port 58081 --app-v2-port 58082 --order-port 58088 --reply-drop-port 58090
pwsh -NoProfile -File deploy/up.ps1 -DeploymentFile runtime/private/xiaomuxia-dev/deployment.json -ValidateOnly
```

prepare 仅生成文件；ValidateOnly 仅做 Compose 配置解析。输出包含自动随机凭据、独立路由、overlay 和 `deployment.json`。保留整个私密目录，不手改 env 或 manifest 端口；输入被修改后哈希校验会拒绝旧 manifest。Windows 应限制该私密目录仅本账户可读。

确认项目和端口后显式启动，再用同一个 manifest 验证：

```powershell
pwsh -NoProfile -File deploy/up.ps1 -DeploymentFile runtime/private/xiaomuxia-dev/deployment.json
.\.venv\Scripts\python.exe deploy/verify.py --deployment-file runtime/private/xiaomuxia-dev/deployment.json --output artifacts/xiaomuxia-h00-001
```

首次启动会拉取 PostgreSQL/Nginx/Python 基础镜像，并构建应用镜像、下载其 Python 依赖；源码库不包含镜像缓存。四个服务为 `postgres`、`app-v1`、`app-v2`、`nginx`；`faults` 未启用，不启动智能体或协调者。数据库不公开宿主端口，三个 HTTP 端口只绑定回环。公共入口为 `http://127.0.0.1:58088`。

验收会写入本次测试订单，固定 30 秒、1 HTTP 请求/秒、30 成功请求、10 个创建→查询→取消流程，前后 `/ready` 及每个业务响应须为 v2，失败/未知/待决为 0；退出码 0 和新目录内 `result.json` 的 `status=passed` 才是通过。下一次验收换 `artifacts/xiaomuxia-h00-002`，不覆盖首次失败。

### 正常停机并保留数据

在同一仓库根目录，用**同一个 project、env 和两份 Compose 文件**。先核对 `ps` 显示的确为自己的四服务，再停止：

```powershell
$ComposeScope = @('compose', '-p', 'incident-pilot-xiaomuxia-dev', '--env-file', 'runtime/private/xiaomuxia-dev/compose.env', '-f', 'deploy/compose.yml', '-f', 'runtime/private/xiaomuxia-dev/deployment.overlay.yml')
docker @ComposeScope ps --all
docker @ComposeScope stop --timeout 15 nginx app-v1 app-v2 postgres
docker @ComposeScope ps --all
```

这是 Docker 官方的 [stop](https://docs.docker.com/reference/cli/docker/compose/stop/)：保留容器、网络和数据库卷，日后仍用原 manifest 执行 up。若明确要移除自己的容器和网络而保留数据库卷，可另选 [down](https://docs.docker.com/reference/cli/docker/compose/down/)：

```powershell
docker @ComposeScope down --timeout 15
```

不加 `-v`、`--rmi` 或 `--remove-orphans`。不要删除 `incident-pilot-xiaomuxia-dev_orders-data`，也不要删除含原凭据的 `runtime/private/xiaomuxia-dev`；重新生成随机密码后挂旧数据库卷会造成密码不匹配。只有确认四服务由自己独占时使用上述项目范围操作。

## 5. Linux：相同独立部署

在新仓库根目录、自己的 Docker 用户上下文运行；不要混用另一个 rootless/rootful daemon。先确认 `docker version`、`docker compose version`，用 `ss -ltn` 查看 58081/58082/58088/58090 是否空闲。Linux 准备时省略 `--wsl`：

```bash
.venv/bin/python deploy/prepare_deployment.py --mode business --output runtime/private/xiaomuxia-dev --project incident-pilot-xiaomuxia-dev --app-v1-port 58081 --app-v2-port 58082 --order-port 58088 --reply-drop-port 58090
INCIDENT_DEPLOYMENT_FILE=runtime/private/xiaomuxia-dev/deployment.json INCIDENT_VALIDATE_ONLY=1 sh deploy/up.sh
INCIDENT_DEPLOYMENT_FILE=runtime/private/xiaomuxia-dev/deployment.json sh deploy/up.sh
.venv/bin/python deploy/verify.py --deployment-file runtime/private/xiaomuxia-dev/deployment.json --output artifacts/xiaomuxia-h00-001
```

`INCIDENT_PYTHON` 可指定自己的绝对解释器路径；默认取本检出的 `.venv/bin/python`。避免遗留旧 `INCIDENT_ENV_FILE`、`INCIDENT_PROJECT_NAME` 或 `INCIDENT_AGENTS=1` 与 manifest 冲突。Linux 生成器会为私密父目录设置 700、私密文件设置 600。

相同四服务的正常停止 / 可选 down（Bash 数组）：

```bash
compose_scope=(compose -p incident-pilot-xiaomuxia-dev --env-file runtime/private/xiaomuxia-dev/compose.env -f deploy/compose.yml -f runtime/private/xiaomuxia-dev/deployment.overlay.yml)
docker "${compose_scope[@]}" ps --all
docker "${compose_scope[@]}" stop --timeout 15 nginx app-v1 app-v2 postgres
docker "${compose_scope[@]}" ps --all
# 仅需要移除自己的容器/网络时另选，仍保留数据库卷：
# docker "${compose_scope[@]}" down --timeout 15
```

Windows 若已有自行维护的 WSL Docker，可在 Windows prepare 命令增加 `--wsl Ubuntu-22.04`，由 manifest 固定发行版，不能把该参数再传给 `up.ps1 -DeploymentFile`。此时所有 Docker 检查与停止也必须走同一 WSL daemon，并将 env/compose/overlay 换成对应 `/mnt/<盘符>/...` 绝对路径；不要照抄上面的直接 Docker CLI 停机命令。主线优先采用一种运行方式，避免交叉操作。

## 6. 工作台可选路径

只改 UI/GET 展示时，可以用一个**不存在的配置文件路径**启动未接入参与者的工作台，输出也独立。Windows 先检查路径不存在，再在前台运行：

```powershell
Test-Path -LiteralPath runtime/private/xiaomuxia-ui-unconfigured.json
# 上一条必须为 False；不要创建该配置文件。
.\.venv\Scripts\python.exe workbench_server.py --port 58766 --config runtime/private/xiaomuxia-ui-unconfigured.json --output artifacts/xiaomuxia-ui
```

Linux 对应：

```bash
test ! -e runtime/private/xiaomuxia-ui-unconfigured.json && .venv/bin/python workbench_server.py --port 58766 --config runtime/private/xiaomuxia-ui-unconfigured.json --output artifacts/xiaomuxia-ui
```

### Windows 真实本地 AIP 工作台：分段准备

这是另一条 Windows 原生路径，要求 **Windows x64 和 CPython 3.12 AMD64**，使用 PostgreSQL 16.15 / Nginx 1.30.6 portable、五个本地参与者、真实 PostgreSQL MCP 和 native supervisor。数据库 MCP 的固定 pglast wheel 对应这个解释器架构；不要用 ARM64 或 32 位 Python 创建这两个环境。它不会自动使用上面的 Docker manifest；不能把 `local-up` 当作四业务 Docker 的下一步混跑。先阅读[本地验收](本地开发验收.md)和[队友部署记录](../deploy-check-record.md) D01–D10。

在**当前用户的普通 PowerShell 7 交互终端**执行，PostgreSQL 必须以非管理员身份初始化/运行。检查当前是否管理员、WMI 查询是否可用以及以下端口；任一被其他实例占用就先停在这里，不按端口杀进程：

```powershell
py -3.12 -c "import platform, struct, sys; print(platform.python_implementation(), platform.python_version(), platform.machine(), struct.calcsize('P') * 8); sys.exit(0 if platform.python_implementation() == 'CPython' and sys.version_info[:2] == (3, 12) and platform.machine() == 'AMD64' and struct.calcsize('P') == 8 else 1)"
$IsAdmin = ([Security.Principal.WindowsPrincipal]::new([Security.Principal.WindowsIdentity]::GetCurrent())).IsInRole([Security.Principal.WindowsBuiltInRole]::Administrator)
$IsAdmin
Get-CimInstance -ClassName Win32_Process -Filter "ProcessId = $PID" | Select-Object ProcessId, ExecutablePath
Get-NetTCPConnection -State Listen -LocalPort 8081,8082,8088,55432,8093,8766 -ErrorAction SilentlyContinue
```

第一条检查应输出 `CPython 3.12.x AMD64 64`、退出码 0；失败时先选择 x64 解释器，不继续创建环境。`$IsAdmin` 应为 False。8081/8082 是应用，8088 是 Nginx，55432 是 PostgreSQL，**8093 是运维 supervisor**，8766 是工作台。正常运行时都属于自己的本地环境。模型端口 8089 不在基础路径中；仅 F12 回复故障辅助才另用 8090。

先完成第 3 节主 `.venv`，再单独安装数据库 MCP，不能把其依赖混入主环境：

```powershell
py -3.12 -m venv .venv-mcp-postgres
.\.venv-mcp-postgres\Scripts\python.exe -m pip --version
.\.venv-mcp-postgres\Scripts\python.exe -m pip install -r domains/database/requirements.txt
.\.venv-mcp-postgres\Scripts\python.exe -m pip check
```

该文件明确锁定 `postgres-mcp==0.3.0` 和 `mcp==1.30.0`。两环境创建/安装任一步失败先处理，不继续启动。

下面把 `deploy/local-up.ps1` 的准备顺序拆开；两种入口均调用 `tools/workbench_host.py --launch`，按本次 session nonce 正常关闭五域。**从数据库准备开始会真实启动服务和写数据库**，只在自己已确认可用的原生环境执行；逐条确认退出码 0，不并行重复启动：

```powershell
# 只校验本地协调配置；明确先使用规则，不调用模型。
.\.venv\Scripts\python.exe tools/configure_local_coordinator.py --disable-llm --check
# 下载/校验/解压项目内 PostgreSQL16.15 和 Nginx1.30.6；需要网络。
.\.venv\Scripts\python.exe tools/download_native_runtime.py
# 初始化本机私密凭据、数据库、应用角色、schema，并启动 PostgreSQL。
.\.venv\Scripts\python.exe tools/prepare_native_database.py
# 启动两应用和 Nginx；保留其受管 PID/路径元数据。
pwsh -NoProfile -File deploy/native.ps1 start
# 生成本地各域配置、最小权限数据库桥接角色，并启动自己的8093 supervisor。
.\.venv\Scripts\python.exe domains/setup_local.py --provision-db --start-supervisor
# 持久写入本地stdio/规则配置；不启用模型。
.\.venv\Scripts\python.exe tools/configure_local_coordinator.py --disable-llm
# 只校验host所需配置和历史事故状态，不启动。
.\.venv\Scripts\python.exe tools/workbench_host.py
# 显式启动：隔离环境，固定8766/五域/默认历史目录，不启动巡检或事故。
.\.venv\Scripts\python.exe tools/workbench_host.py --launch
```

`setup_local.py --install` 也可安装独立 MCP 环境；上面已显式完成安装，故不重复。生成的资源密码和审批密钥仅保存在 `runtime/private`，不输出到 Git。下载器把官方来源记在 `tools/runtime/sources.json`，校验 ZIP CRC 和必需文件；坏缓存会保留并报错，应先检查错误，不删除数据库来解决软件解压问题。host 固定复用 `artifacts/high-score-workbench`，发现运行中事故或待批审批会拒绝启动；不支持在此入口任意改端口/配置/输出，也不与 `start_workbench.ps1` 同时启动。

工作台成功不能只看页面能打开：

```powershell
$State = Invoke-RestMethod -Uri http://127.0.0.1:8766/api/state -NoProxy -TimeoutSec 5
$State | Select-Object connected, mode, pid, connection_error, config_sha256
$State.participants
(Get-FileHash -LiteralPath runtime/local-coordinator.json -Algorithm SHA256).Hash.ToLowerInvariant()
.\.venv\Scripts\python.exe deploy/verify.py --url http://127.0.0.1:8088 --output artifacts/xiaomuxia-native-h00-001
```

要求 `connected=true`、`mode=local-aip-stdio`、无 `connection_error`，返回的 `config_sha256` 与当前配置文件一致，参与者为自己的五个本地角色；H00 单独通过。页面可见、HTTP200、进程仍在不等于这些门槛通过。

| 现象 | 先查什么 / 如何继续 |
| --- | --- |
| venv `ensurepip`/临时目录 PermissionError | 先确认当前账户目录/临时目录可写；保留失败原文，切回自己正常交互终端完成同一安装，不继续使用半成品 venv。 |
| PostgreSQL 提示不能以管理员运行 | 回到同一用户的非管理员终端；检查已有 `runtime/pgdata` 与进程，不重复 initdb，不删除数据。启动错误看 `runtime/postgres.log`。 |
| WMI AccessDenied、子进程 PermissionError 或工作台超时 | host 日志在 `artifacts/workbench-host-8766/<session_nonce>/stderr.log`；旧 `start_workbench.ps1` 日志在其所选输出下 `server-*.stderr.log`。区分受限执行器和普通交互终端，核对 `runtime/workbench-server.json`、返回 PID、CIM 的解释器/命令行归属；失败可能已留下业务服务，不盲目整条重跑或把 PostgreSQL 提权启动。 |
| 8093 冲突或 supervisor 不就绪 | 看 `runtime/ops-supervisor.pid` 和 `runtime/ops-supervisor.stderr.log`；`setup_local` 对已有 supervisor 做认证及项目路径核验。其他目录的实例不能复用。 |
| 页面存在但配置 SHA/mode 不同 | 这是旧配置/其他实例；保存记录，确认事故空闲，核实属于自己后才正常关闭旧工作台。新启动器会明确拒绝，不能以“端口已开”判定成功。 |
| 中文目录 / 盘符别名错误 | 看 `deploy/native-runtime.json` 的 `native_drive` 和 `nginx_bin`；native 脚本会核对别名是否同一目录，不能覆盖已被其他目录占用的盘符。 |

### 上述 native 路线的收尾

先结束自己发起的事故和审批，再按本次 host 的元数据请求空闲停止：

```powershell
$HostMetadata = Get-Content -LiteralPath runtime/workbench-server.json -Raw | ConvertFrom-Json
.\.venv\Scripts\python.exe tools/workbench_host.py --stop --pid $HostMetadata.runtime_pid --nonce $HostMetadata.session_nonce
```

`OWNED_IDLE_STOP_REQUESTED_NOT_YET_CLOSED` 只表示请求已写入，不代表进程已关。保持不再提交新事故，等待该 session 下的 `finished.json`，然后读取：

```powershell
Get-Content -LiteralPath (Join-Path $HostMetadata.control_directory finished.json) -Raw | ConvertFrom-Json
```

要求 `status=LOCAL_CONTROLLED_WORKBENCH_NORMAL_CLOSE`、五个 `worker_exit_codes` 全0，且配置/源码未变；等待期间 `stop-observation.json` 会指出是否仍有事故、审批或任务。没有正常 finished 不能先停其数据库/MCP 资源。nonce 仅适用于自己刚启动的 host，不用于旧 `start_workbench.ps1` 进程。

host 正常关闭会结束其五域和 MCP，但独立 8093 supervisor 按设计继续存活。它当前没有优雅关闭 API；确认属于自己的本次原生环境后，使用已有进程核验工具绑定 PID 和绝对脚本路径，先只读核对，再显式终止这一个 supervisor：

```powershell
$RecordedOpsSupervisorPid = [int](Get-Content -LiteralPath runtime/ops-supervisor.pid)
$OpsSupervisorScript = (Resolve-Path -LiteralPath domains/ops/native_supervisor.py).Path
# 实际监听可能是venv shim的孩子，不能只结束pid文件记录的shim。
$OpsSupervisorPid = [int](Get-NetTCPConnection -State Listen -LocalPort 8093).OwningProcess
Get-CimInstance -ClassName Win32_Process -Filter "ProcessId = $OpsSupervisorPid" | Select-Object ProcessId, ParentProcessId, ExecutablePath, CommandLine
.\.venv\Scripts\python.exe business/native_process.py --pid $OpsSupervisorPid --script $OpsSupervisorScript
# 上一步身份核验成功，且host已正常关闭后，才终止该独立supervisor：
.\.venv\Scripts\python.exe business/native_process.py --pid $OpsSupervisorPid --script $OpsSupervisorScript --terminate
# 最后停止自己的业务应用、Nginx和PG，保留数据库/配置/日志。
pwsh -NoProfile -File deploy/native.ps1 stop
Get-NetTCPConnection -State Listen -LocalPort 8081,8082,8088,55432,8093,8766 -ErrorAction SilentlyContinue
```

8093 已无监听时跳过 supervisor 终止，不复用过期 PID。实际监听进程命令行必须指向本检出的 `domains/ops/native_supervisor.py`；可用 `ParentProcessId` 与 `$RecordedOpsSupervisorPid` 追溯 shim，但不能只凭父 PID 停进程。

原 `native.ps1 stop` 可能只结束受管的 venv shim，遗留实际应用孩子。因此必须检查监听和实际命令行；如果 8081/8082 仍有本项目应用，逐个按真实监听 PID、绝对脚本和版本核验后终止。下面是**仅在 8081 仍监听时**的 v1 示例：

```powershell
$AppChildPid = [int](Get-NetTCPConnection -State Listen -LocalPort 8081).OwningProcess
Get-CimInstance -ClassName Win32_Process -Filter "ProcessId = $AppChildPid" | Select-Object ProcessId, ParentProcessId, ExecutablePath, CommandLine
.\.venv\Scripts\python.exe business/native_process.py --pid $AppChildPid --script run_app.py --version v1
# 上一步成功且实际命令行为本检出的business/run_app.py --version v1 --port 8081，才继续：
.\.venv\Scripts\python.exe business/native_process.py --pid $AppChildPid --script run_app.py --version v1 --terminate
```

v2 相同两步，把端口替换为 8082、版本替换为 v2；不是本检出脚本或版本不匹配就停止处理。Nginx 和 PostgreSQL 使用 `deploy/native-runtime.json` 中的实际 `nginx_bin/nginx_prefix/postgres_bin/pgdata`，`native.ps1 stop` 会调用各自控制工具；仍有残留时核对该元数据与进程命令行，不临时改成默认路径或删除 pid/数据文件。

末次重新检查上述六端口和自有进程，应均已退出；不按名称全杀 Python。`native.ps1 stop` 单独执行只管理业务底座，完整 `local-down` 一键入口仍缺。上面的 supervisor/残留应用步骤是明确终止已核实进程，不冒充其优雅关闭；需要简单可复制的正常停机主线时优先选第 4/5 节 Docker 四业务。

`deploy/local-up.ps1 -Install` 是上述准备的一键编排入口，末步同样启动受控 host；正常关闭按上面的 `workbench_host.py --stop --pid ... --nonce ...` 步骤执行。它不替代这些前置和失败排查。旧 `tools/start_workbench.ps1` 仍用于历史入口，不与此 host 同时启动，其进程也不能用 host nonce 停止。`-EnableLocalModel` 仅显式选用[本机 Qwen 配置](local_model_workbench_20261018.md)，不下载或启动模型。Linux 完整原生链路没有对应的一键入口。

正式七角色路径见 [ISOLATED.md](../deploy/ISOLATED.md)，需自己已注册的七身份/证书和独占 Inbox；四业务准备没有可用于故障注入的 `target.json`。正式 Kafka/Monitor 仍需官方连接配置。当前文档没有让接手者运行故障、共享身份消费者或付费模型。
