你的智能体要干什么、怎么开发

配合《高分方案_需求架构创新与任务_20261017.md》阅读。这一页只讲三件事：每个智能体是谁、一次故障里它们怎么配合、代码从哪里下手。

先用一个比喻：医院多科会诊。 病人（订单网站）突然出问题，总值班医生（协调智能体）自己不能碰任何检查设备，只能请各科医生（应用、数据库、运维智能体）用本科室的设备检查，再根据结果决定下一步查什么、谁来治。各科的设备钥匙（账号密码）从不交给别人，这就是“凭据不出域”。
梧桐平台 = 医院系统挂号建档（注册）、按科室找医生（发现）、拉会诊群（群组通信）、监控与记录（AMP 日志）
协调智能体 = 总值班医生不动手，只问诊、开检查单、定治疗方案、写病历
各域智能体 = 专科医生只能用自己科室的设备，查完把结果报回来
业务验证智能体 = 复查科治完之后真的下几单，确认病人好了
操作账本 = 手术记录本某医生中途离开，接班医生先看记录，做过的手术不再做第二遍

一、有哪些智能体，分属谁

业务负责人（协调机，可以就是你的电脑）

协调智能体 无任何资源密码
已有 leader 身份，要改造：从“固定顺序”变成“看证据决定下一步”
业务验证智能体
已有 verification 身份：持续下单、查单、取消，判断业务是否真的恢复

另有“故障工作台”网页：发起事故、看证据、点审批、看结果。

三个“组织”（资源机，本地 Docker 里跑）

应用智能体 持有：应用管理权限
已有 application 身份 · 管订单网站本身
数据库智能体（主 + 备） 持有：数据库账号
已有 database 身份 + 新注册一个“备” · 内部 = 网关 + 开源 Postgres 工具
运维智能体 持有：Docker 权限
新注册 · 内部 = 网关 + 开源 Docker 工具 + 自写路由工具
梧桐平台（wt.ioa.pub） —— 所有智能体之间的消息都经过这里，互相之间不直连
注册 / 证书ADP 按技能发现AMQPS 群组任务AMP 日志 → 访问量

二、每个智能体具体能做什么

智能体它能“看”（观察，只读）它能“做”（修改，要记账）它绝不做
协调收各方报回的结果；读平台上各智能体的心跳决定下一步派谁查什么；生成恢复计划；必要时找替补直接连数据库、Docker、网站后台
应用网站最近的报错、当前版本、连接池占用、直连网站能否读写回退应用配置；重建数据库连接池改数据库设置、重启容器
数据库数据库是不是只读；有没有长事务锁住表；连接数；某个请求键的订单回执把只读改回读写；结束指定的卡住会话（只限实验业务用户）执行任意 SQL；碰白名单外的库
运维容器是不是退出了、容器日志；网关当前转发到哪个版本重启带项目标签的容器；把路由切回已登记的版本操作别的容器；写任意网关配置
业务验证每秒一单的成功/失败/未知统计；原来超时的那单到底成没成用原请求键补办用户原本要做的事改任何资源

三、一次故障从头到尾（主演示场景 F10 + F15）

故障：有人把网关指回了旧版本，同时数据库被设成只读。处理到一半，数据库智能体进程崩了。

1
业务验证发现下单从成功变成 502，工作台亮红。你点“发起事故”。
2
协调→梧桐 ADP“给我找会查应用、数据库、运维的智能体”。平台返回候选名单；协调者拉一个会诊群，用 Inbox 邀请它们入群，再问每个人“你管哪些资源、会哪些工具”。
3
协调同时派两个检查单： 
→ 运维：{"kind":"observe","tool":"ops.route_status"}
→ 应用：{"kind":"observe","tool":"app.recent_errors"}
运维回报：“网关转发到 v1（旧版）”。应用回报：“v2 直连能读，但写入报 read-only 错误，我怀疑是数据库的问题”。
4
协调把症状和结果交给大模型：“可能原因有哪些？” 大模型列出：路由错、数据库只读、应用容器挂了……排序规则算出“查数据库只读”最能区分剩下的原因，于是派： 
→ 数据库：{"kind":"observe","tool":"db.read_only_status"}
数据库回报：“default_transaction_read_only = on”。原因收敛为两个：路由错 + 数据库只读。
5
协调生成计划：①回退路由 → ②恢复读写 → ③重建应用连接池。②是高风险，工作台弹窗，你点“批准”。
6
运维执行①，路由切回 v2。数据库（主）收到②，先在账本写“op-2 执行中”，执行成功，账本改为“已完成”——正要回报时进程崩了。
没有账本的话，协调者不知道 ② 做没做，只能重做或干等。
7
协调等不到回报，问状态也没回应 → 判定掉线。重新去ADP找同技能的候选，找到数据库（备），邀请入群，发“交接包”（已知证据、剩余任务、op-2 状态未知、新的隔离令牌）。
8
数据库（备）查同一本账本：“op-2 已完成”，再实际查一次数据库确认可写 → 回报“已完成，跳过，不重复执行”。旧的主进程即使活过来，拿旧令牌也改不了任何东西。
9
应用执行③重建连接池。业务验证处理故障期间超时的那几单（按原请求键查到底成没成），再连续下单 30 秒，全部成功。
10
协调结案，工作台显示：每一步依据了什么证据、谁做了什么修改、接管过程、业务曲线。所有任务都在梧桐平台留有记录，每次访问都通过 AMP 日志计入平台后台访问量。

四、智能体的代码长什么样

1. 参与者骨架 已有

现有 integration/wutong_incident.py 里的 BusinessTask 已经做好了：连梧桐、收任务、接受 → 执行 → 回报结果。所有参与者共用这套骨架，不用重写。

收到任务(start)
  → accept / working
  → output = execute_business_action(...)   ← 只有这里因角色不同
  → submit_for_completion(结果)

2. 工具箱 主要新写

“开发一个智能体”基本就是给它写工具箱：一个工具名对应一个函数，函数去操作本组织的资源，返回事实。

TOOLS = {
  "db.read_only_status": 查只读设置,
  "db.blocking_sessions": 查锁,
  "db.set_read_write":   改回读写,  # 高风险, 要审批+记账
}
def handle(task):
    检查 发送者是不是协调者
    检查 工具在不在白名单
    如果是修改 → 先查账本, 再执行, 再记账
    return {"facts": [...], "operation": {...}}

数据库和运维不用自己写这些函数：网关把开源 MCP 工具自动变成这张表（创新二）。

3. 协调者 = 决策循环 改造

现在是写死的 8 步顺序。改成循环：

发现参与者, 拉群
while 没恢复 and 没超预算:
    假设 = 大模型(症状, 已有证据)
    下一步 = 排序规则(假设, 可用工具)
    结果 = 派任务给对应智能体
    更新证据, 每一步写入任务日志
    if 原因确定: 生成计划 → 审批 → 依次执行
    if 有人掉线: 找替补 + 发交接包
业务验证 → 结案
