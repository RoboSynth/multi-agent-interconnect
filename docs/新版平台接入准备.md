# 新版正式平台接入准备

## 2026-10-18 证书已齐备

七个新版身份均已从登录后的官方 Registry 详情页逐角色核对名称、AIC 与审核通过状态。用户重新明确授权后，七份 EAB 经官方登录会话各领取一次并移入项目独立私密目录；官方 CLI 为七角色分别签证，真实退出码均为 0，证书 CN=AIC、clientAuth、当前有效期和私钥匹配检查全部通过。证书均有效至 2026-12-06 对应 UTC 时刻，原四身份保留。

[安全办理摘要](../evidence/platform-certificates-20261018/summary.json)只包含公开身份、证书摘要、期限、退出码和校验结论；私钥、EAB 与原始签证日志保存在本机私密目录。旧的审核中、五个详情已核实和证书暂缓记录保留为历史，不再代表当前状态。

七个新版 AIC 的官方 ADP 精确只读查询随后全部通过，公开 Inbox 端点与登记模板的身份绑定一致，见[元数据观察](../evidence/platform-certificates-20261018/adp-identity-observation.json)。这解决了证书与公开身份元数据核对缺口；按技能组队、AMQPS describe/任务往返、隔离容器业务恢复与接管仍须分别运行并留证。本地模型工作台的健康验证不替代这些验收。

## 初始准备与 2026-10-17 历史记录

新版平台配置由 `domains/setup_platform.py` 从既有
`integration/private/incident/config.json` **只读生成**。脚本不注册身份、不修改已审核
ACS、不复制证书或私钥正文，也不读取资源环境文件内容。每次生成新目录，保留旧证据。

```powershell
.\.venv\Scripts\python.exe domains/setup_platform.py
```

当前可供只读联调的初版目录为 `runtime/platform-preparation-20261017T092958Z/`。
后续重新生成时，以命令输出的新目录及其 `readiness.json` 为准。

| 文件 | 持有内容 | 明确不包含 |
| --- | --- | --- |
| coordinator.json | 协调者自身 AIC/证书路径、公开 ADP/MQ 地址、粗技能查询、独立审批环境文件引用 | 参与者私钥、数据库与应用环境、Docker/运维 token |
| application.json | 应用方自身证书、协调者白名单、应用本地域环境文件引用与管理端地址 | 数据库管理员、其他身份私钥 |
| verification.json | 验证方自身证书、公共订单入口与观察时长 | 应用/数据库管理环境 |
| database.json / database-bridge.json | 数据库方自身证书、只在数据库进程加载的 MCP 环境文件引用、策略、共享账本 | 协调者私钥、应用管理凭据 |
| database-backup.json / database-backup-bridge.json | 与数据库主共享同一账本；新身份留空待注册 | 编造的 AIC 或复用主身份私钥 |
| ops.json / ops-bridge.json | 运维方本地域工具/策略引用；新身份留空待注册 | 数据库凭据、编造的 AIC |

现有 leader/application/database/verification 四个身份有本机配置引用；生成脚本最初为
database-backup 与 ops 预留新身份，配置草稿中的 AIC、端点、证书与私钥字段为 `null`，状态为
`not_registered`，签发与审核后才可填写。脚本未验证这些证书当前是否有效、端点是否
在线或新运行器是否已在平台跑通，`readiness.json` 不把离线准备标为在线验收完成。

`acs/` 中的草稿使用中性的 `provider.name=Incident Pilot`，不复制旧 provider 的个人
信息。已存在 AIC 的原值仍须保留；AIC 中的平台命名空间不能当作 provider 字段删除。
所有草稿都以 `active=false` 输出，并经固定版本官方 Registry JSON Schema 与 SDK
模型真实离线校验。离线通过不等于平台审核通过。

| 身份 | ACS skill id | 接入动作 |
| --- | --- | --- |
| 协调者 | incident.coordinate | 保留技能 ID，描述更新为 ifc/1.0 跨域协同 |
| 应用方 | incident.application | 保留技能 ID，描述更新为 PostgreSQL 订单应用与受控恢复 |
| 验证方 | incident.verification | 保留技能 ID，描述更新为原请求解析与业务观察窗口 |
| 数据库主/备 | db.observe、db.act | 旧主身份技能为 incident.database；平台禁止改已通过身份，使用新版独立身份，备也需独立注册 |
| 运维方 | ops.observe、ops.act | 新身份注册；细工具与资源范围在 describe 中确认 |
| 接入体检 | aip.onboarding.check | 新身份；只读官方 ADP/ACS、协议、AMQPS Inbox 与技能检查，不主动探测第三方目标 |

2026-10-17 正式登记进展保存在
`integration/incident/high-score-registration-20261017/`。实际页面与固定官方
`registry-server/app/agent/api.py` 一致：已通过身份不可再编辑。原四个 0.2.0 身份、
证书及审批记录保留；新版拟使用七个独立身份。新提交草稿的 AIC 为空，不能把旧 AIC
填入新登记；本机生成的联调配置仍须在新身份真实获批、签证后更新。

| 新版身份 | 截至本轮实读的状态 | 证据 |
| --- | --- | --- |
| 运维 | 已提交一次，审核中，AIC 尚未分配 | ops.review-observation.json |
| 数据库备 | 已提交一次，审核中，AIC 尚未分配 | database-backup.review-observation.json |
| 协调、应用、数据库主、验证、接入体检 | 用户明确授权后各提交一次，均审核中，AIC 尚未分配 | 对应 *.submission.acs.json / *.validation.json / *.review-observation.json |

提交用 ACS 复用私密目录中已核实的 provider 资料，正文不写入本文。首次尝试提交新增
数据库主身份曾被自动审批拦截，动作未执行；随后用户明确回复“授权提交这五个新版身份”，
五份草稿已逐一正式提交并保存真实审核中状态。原自动审批记录保留，不通过其他方式绕过。
审核中状态不能当作已登记可用或已签证。

数据库/运维 ACS 草稿根据本地策略中的已声明工具目录聚合，`readiness.json` 明确标注
这次准备不是远程 `tools/list` 探测。运行器启动时仍须执行真实 `tools/list` 并校验所有
策略工具存在。新工具不会造成粗技能 ID 频繁变动。

新版独立参与者入口为：

```powershell
.\.venv\Scripts\python.exe incident/platform_worker.py --config <本域配置绝对路径>
```

同一 AIC 只运行一个 Inbox 消费进程。应用与验证方可先使用已有身份做新版只读 AIP
契约联调；数据库新技能审核、运维及备身份准备完成后，再进行完整发现与协作验收。
协调者必须通过 ADP 查询并经群组 describe 确认资源和工具，不能把配置草稿当成发现结果。

## AMP 六类日志与转发

`BridgeGroupRuntime` 接收本域 `AmpRuntime`，将官方 MessageEmitter 与 AccessEmitter
传给 Leader 及每个 Partner；业务 handler 在 join 启动消费前绑定，返回真实业务
`status`，避免首个任务漏打或被计为假成功。Heartbeat/Metrics 周期任务、System
进程事件、带证书的 Audit 由本域 AmpRuntime 管理。首次 Start 计一条 access，Complete、
Get 与重放仍有 message 边事件。独立 `serve_platform` 入口也创建这套完整 AMP。

项目内便携程序位于 `tools/runtime/fluent-bit-5.1.3/`，来源与官方 SHA256 见
`deploy/fluent-bit/portable-source.json`。配置按固定官方 Monitor 的六个 `amp.*` topic
映射生成。未取得梧桐 Kafka broker 与认证信息前，默认只输出本地 stdout：

```powershell
pwsh -NoProfile -File deploy/fluent-bit/run.ps1 -Mode stdout -LogDirectory <本域 AMP 目录>
.\.venv\Scripts\python.exe deploy/fluent-bit/verify_local.py
```

本地真实便携程序验收证据：`output/fluent-bit-local-20261017T093249Z/results.json`。
audit、heartbeat、metrics、access、message、system 六个 tag 各输出 1 条，原 log_id 均
保留。这是**合成本地记录的真实 Tail→stdout 验证**，未连接 Kafka、未证明平台入库。

Windows 实测要求：中文路径通过已登记的 P: ASCII 别名读取；Tail 的 glob 路径使用
反斜杠。测试用 `Exit_On_Eof` 正常退出并刷出 stdout，持续转发配置不启用该选项。
JSON parser 保留 timestamp，转发不改原 body；audit 只允许官方 `_fb_ts` 附加元数据，
Monitor 会在验签前按官方规则剥离。每类 Tail 使用独立 offset DB，日常不从头重发。

取得赛方配置后，将 `deploy/fluent-bit/kafka-settings.example.json` 复制到本域私密
目录，填写**经确认**的 broker、security.protocol、TLS/SASL 参数和 topic 权限。
密码使用 `${AMP_KAFKA_PASSWORD}` 环境引用；渲染器拒绝缺 broker、缺安全协议或明文
密码的 Kafka 配置。六类 topic 的预建/LogAppendTime 要求按赛方与官方 Monitor 确认；
模板关闭自动建 topic。不能把官方本地开发示例的 localhost:19092 当成梧桐配置。

```powershell
pwsh -NoProfile -File deploy/fluent-bit/run.ps1 -Mode kafka `
  -LogDirectory <本域 AMP 目录> -KafkaSettings <本域私密配置绝对路径>
```

后续在线验收依次保留：六类日志本地记录、发送方成功与失败统计、Kafka/Monitor 查询、
Audit 验签结果、按事故与 task ID 的访问对账、Discovery 存活视图。仅能连接 Kafka
端口不足以说明认证成功或数据入库。

[Fluent Bit Windows 便携包](https://docs.fluentbit.io/manual/installation/downloads/windows.md)、
