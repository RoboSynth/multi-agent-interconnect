## 二 必须先立的四条规矩

**1. 今天就把代码放进 Git。** 现在项目目录没有 Git，多人改同一份文件夹一定会互相覆盖。

- 建私有仓库（Gitee、AtomGit 或 GitHub 均可），甲负责。
- 首次推送前确认这些不会被上传：`integration/private/`、`*.key`、`*-eab.json`、`deploy/.env`、`runtime/`、`.venv*/`、`tools/runtime/`（现有 `.gitignore` 已覆盖，推送前再用 `git status` 和 `eval/secret_scan.py` 检查一遍）。
- **注意：现有 `.gitignore` 忽略了整个 `vendor/`，而 SDK 改造就在 `vendor/ACPs-community` 里。** 这部分不会进主仓库。处理办法：把改造后的 ACPs 推到单独的 fork 仓库（即 T01），主仓库通过 git submodule 或固定提交号引用它。这一步在多人开始改代码之前完成，否则队友拿到的是没有改造的官方 SDK。
- 每人一个分支，小步提交，通过合并请求进入 `main`，甲每晚合并。

**2. 正式身份只在一台电脑上运行。** 同一个 AIC 只能有一个进程在收 Inbox 消息。两台电脑同时运行同一身份，消息会被两个进程随机分走，表现为任务时好时坏、极难排查。

- 证书、私钥和正式身份只放在甲的“常开电脑”上，它负责所有梧桐联调和长期运行。
- 乙、丙在自己电脑上用本地通道开发（`incident/local_transport.py`，`local-*` 身份），不需要证书。本地结果只作为开发证据，正式数据以甲的平台运行为准。

**3. 数据契约只有一份。** `incident/contracts.py`（ifc/1.0）是所有智能体之间消息格式的唯一来源。任何人要改字段，先在群里说明，改 `schema_version`，同一次提交里改全部受影响的发送方和接收方。

**4. 统一的“完成”标准。** 一项任务算完成必须同时满足：`tests/` 全部通过；本地 F10 能跑通；把证据文件路径写进 `开发进度_高分方案.md` 自己那一节。没有证据文件的“做完了”不算。

## 三 日常节奏

- **每天固定时间 15 分钟同步**（例如晚上 10 点）：每人只说三件事——昨天拿到了什么证据、今天要拿到什么、卡在哪。
- **进度文档分区写**：`开发进度_高分方案.md` 按甲、乙、丙分三节，各写各的，避免互相覆盖。
- **每晚集成**：甲合并当天代码，在常开电脑上跑一次 F10（本地）+ 一次梧桐巡检，结果发群里。哪个合并导致失败，由提交人第二天上午先修。
- **用 AI 写代码时**：每人的 AI 助手只改自己工作线的目录；不要让两个 AI 同时改同一个文件；给 AI 下任务时附上方案文档和任务编号（如“完成 T45 中的 M1”）。

## 四 现在最需要拍板的一件事：大模型

当前 M2 默认用规则假设集，开发阶段没有调用真实模型。但创新三和“AI 技术应用”评分都需要真实的大模型调用，M1 对照也必须用同一个模型。乙今天要定下：用哪个模型（OpenAI 兼容接口的国产模型即可）、谁的 API 账号、总预算多少；定好后写进 `docs/模型配置.md`（API 密钥只放本机环境变量，不进仓库），正式评测前冻结模型版本和参数。
