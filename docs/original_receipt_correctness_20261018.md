# 原请求回执正确性修复（2026-10-18）

旧验证方把 HTTP 200 且带 v2 标记的回执直接认作原请求已解决。纯模拟 HTTP 已复现两个反例：只有版本字段，以及错误原键且结果为 unknown；即使新业务健康，它们也不足以证明原订单结果。

本修订由业务观察器与验证方共用 `business/receipts.py`。回执必须绑定原 operation_key、明确 outcome=committed、提供合法 UUID 订单号，并与 order.id 一致。创建回执校验原创建键和 CREATED 快照；取消回执保留独立创建键，校验 CANCELLED 快照，允许 changed=false。观察器已知原操作类型或订单号时，也必须匹配。按原键读取回执，不另建替代订单，也不以当前订单状态否定历史提交快照。

无效回执保持原请求未决；验证方仍单独执行新订单健康观察。新业务健康与原请求解决必须同时成立，才能认定业务恢复。只有原键而没有原始业务内容时，本修订不声称证明了原 item/quantity 与请求内容完全一致。

离线验证共 21 个不同测试方法（9 个验证方、8 个版本契约、4 个观察器及协调集成），均正常退出 0。集成检查使用真实观察器、验证方和协调器，HTTP 为 MockTransport，时间为虚拟时钟；包含原回执一次加新订单 30 次/10 流程，仍因错误回执保留人工处理。它不构成新的真实 F12/E5、平台或 30 秒实跑验收。受限 Windows 环境中的挂起检查已结束，失败记录保留。

代码在基于团队 f7c2b16 的独立修订中完成；本机旧运行环境及旧 E1 计划的 204 个冻结输入保持原字节。另经核对，旧 revision3 的公开源集合为 157，而当前 runner 动态要求 158，多出 incident/workbench_access.py；因此旧计划不能直接在当前源树执行。未来部署或正式 E1 必须建立新的源、镜像、配置和目标绑定，不能复用旧计划哈希。既有未确认实验、原未决请求及坏日志均未被本修复重新判为成功。
