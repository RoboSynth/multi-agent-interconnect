# F12 / E5：公共入口丢回复后的原请求确认

新版入口为 `eval/unknown_receipt_experiment.py --plan …`。默认只检查本地文件；仅准备计划或运行离线测试不代表真实 F12、平台通信或 E5 已通过。旧 `--env-file` 容器入口保留兼容，历史证据不改写，也不计为本版正式结果。F12 不加入 E3 矩阵。

## 条件与范围

使用 `deploy/prepare_deployment.py` 生成的独立 **seven** 部署及其自己的协调配置，正常启动后提供明确 target。target 使用 `incident-evaluator-target/1.0`，四个不同回环端口为 `app_v1/app_v2/order/reply_drop`；旧三端口 target 仍可用于原场景，但不能执行 F12。

四个业务容器及六个资源域必须已运行。注入器复核它们的容器 ID、镜像 ID、StartedAt、标签、源代码、域身份、挂载与端口；正式 ADP 选择和 describe 结果再绑定这些域。reply-drop 必须使用当前 app-v2 的同一已有镜像，挂载为空，使用本项目网络和第四回环端口。不会 build/pull、接管已运行 proxy 或替换现有业务容器。

协调者的证书、私钥、trust、approval 文件路径必须为项目内绝对路径。计划冻结目标、配置、这些私密文件和现有 evaluator/domain/SDK 源的哈希，不把凭据内容写入计划。先停止同一身份的工作台、巡检及其他 Inbox 消费者；复用已有协调者身份锁只限制本机同锁目录内的协作入口，不能排除另一台机器或另一 checkout。

## 离线准备和检查

在自己的 checkout 根目录操作，将示例路径替换为此次独立部署的文件。输出必须是尚不存在的 `eval/results/platform/…` 目录；计划与输出分开，所有路径必须留在当前 checkout 内。

```powershell
$repo = (Get-Location).Path
$python = Join-Path $repo '.venv/Scripts/python.exe'
& $python (Join-Path $repo 'eval/unknown_receipt_experiment.py') --prepare --plan runtime/private/f12-e5-plan.json --target-config runtime/private/my-seven/target.json --config runtime/private/my-seven/domains/coordinator/config.json --output eval/results/platform/f12-e5-my-run
& $python (Join-Path $repo 'eval/unknown_receipt_experiment.py') --plan runtime/private/f12-e5-plan.json
```

Linux 使用当前环境的 Python 执行同一脚本，参数不变。文件或源码改变后重新准备一个新计划，不能复用已授权的旧哈希。准备不读取 Docker 状态，不连接梧桐，不调用模型。

## 显式执行

实际执行需要单独的授权文件；`--execute` 本身不构成授权。授权须在审阅计划并获得明确许可后写入，字段必须精确为下表，其中布尔值均须为 JSON `true`，不能用 `1` 替代。

| 字段 | 值 |
| --- | --- |
| `schema_version` | `platform-f12-authorization/1` |
| `authorized` | `true` |
| `plan_sha256` | 计划文件原字节 SHA-256 |
| `experiment_id`, `project`, `output`, `effects` | 与计划逐项相同 |
| `exclusive_coordinator`, `no_other_identity_consumers`, `no_active_or_unknown_operations` | `true` |

```powershell
& $python (Join-Path $repo 'eval/unknown_receipt_experiment.py') --plan runtime/private/f12-e5-plan.json --execute --authorization-file runtime/private/f12-e5-authorization.json
```

协调进程环境须去除 PostgreSQL/远程 Docker/资源凭据变量；资源凭据留在各域。执行仅运行这一例：公共入口提交两条随机原键的订单，在真实回复超时后以绑定数据库计数佐证已提交。第一个原键交给真实 `IncidentCoordinator`，第二个原键仅留评估器私有记录，作为缺键对照。

协调器只接收普通症状与原键，依据 `route_version=unknown`、`application_reachable is True` 和本次 `route_sha256` 的正常工具事实，调用现有 `ops.route_rollback`，重新观察 v2，再由 `VerificationPartner` 查原键并验证业务。未知路由动作须成对携带 `expected_route_version=unknown` 与精确 SHA；默认无参数路径仍要求当前 v1。真实 Bridge/OperationLedger 保持 fence 和版本前置，route MCP 再核当前文件原字节、直连登记 v2 的 `/ready`，写前二次比对文件；变化或不健康即失败，目标固定为 v2。故障标签、注入原因、SQL 结果不会交给诊断者。评估器不会先恢复路由来替代协调器恢复。

原回执须匹配原操作键、committed、create、UUID 订单 ID 及快照身份；同键重试须返回同一订单，数据库仍仅一行。缺键事件即使完成新的健康流程也须为 `needs_attention/manual_required`，不得收到评估器隐藏的原键或替代载荷；唯一实验 item 的总订单数仍为两条。健康验证自身的新订单不算原意图替代订单。

最后先正常关闭本组 transport，再在 `finally` 用同一注入器恢复原路由字节并只停止本次唯一 session 的 proxy；关闭失败也会尝试恢复。独立 H00 使用公共入口 v2，前后 `/ready` 为 v2，30 秒、30 成功请求、10 完整流程，失败/unknown/未解决/pending 均为零。任一环节失败均不记通过，保留最初错误、清理错误及异常组子错误；不自动重试。

## 证据与离线验证

`result.json` 保存各项判据与错误；`private/` 保存原始请求键、配置引用、协调任务/事件、注入 ownership proof 和 transport 记录；`restored-h00/` 保存独立原始观测。保持该目录私密，团队共享前按项目上传流程筛选，不能直接公开私钥或环境文件。复用现有 `close_owned` 检查本地 group/inbound/inbox/connection/本组 MQ 状态与四类 cleanup warning，任一不合格均失败；没有这四类 warning 不代表 stderr 全空，也不能证明远端 ACL 已清空。

```powershell
& $python -B -m unittest discover -s (Join-Path $repo 'tests') -p test_unknown_receipt_target.py -v
& $python -B -m unittest discover -s (Join-Path $repo 'tests') -p test_f12_planner.py -v
```

测试采用真实协调器、验证器、订单观测器及 ops Bridge/OperationLedger/route MCP；HTTP 为 MockTransport，数据库为临时 SQLite，路由工具仅替换外部进程和 HTTP 资源 IO，时钟为虚拟时间。它们验证控制流和判据，不能替代真实 Docker、AMQPS、故障效果或实际 30 秒验收。
