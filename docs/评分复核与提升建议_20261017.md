# 评分复核与提升建议（智能体互联赛道）

复核对象：`docs/完整架构与业务设计.md`、`docs/分阶段开发计划与评分映射.md`、`docs/故障场景与评测设计.md`，以及 `integration/platform-status.json` 记录的 v0.2.0 实际状态。评分依据为官方《附件1 AIC·智能体互联竞赛规则及作品提交要求》和《附件2 技术报告参考大纲》。复核日期 2026-10-17，距初赛截止（10-30 20:00）约 12 天。

## 一 结论

方案的工程质量高、评测设计严谨，梧桐平台全流程（4 身份审核通过、证书、ADP 发现、10 个正式任务）已经跑通，必要验证场景这一关基本过了，这是最大的优势。

但按评分表逐项对照，有三个结构性问题会让分数卡在中档，且不是“多做一点”能解决的：

1. **官方开源代码零改造。** `vendor/ACPs-community` 与 v2.2.0 相比除换行符外没有任何修改；设计文档也明确“保留官方 GroupLeader、Partner、ADP 和传输实现”。而创新性高档（18-25）的第一句是“基于智能体互联开源代码深度二次开发”，技术应用中档描述是“代码复用改造程度一般”，答辩 PPT 要求“重点展示开源代码改造逻辑”。两项创新（探测排序、成员接续）目前都放在应用层，评委看到的会是“调用 SDK 做了一个运维应用”。
2. **需求分析讲的是运维痛点，不是互联痛点。** 评分表高档要求“精准剖析异构智能体互联行业痛点”，中档的扣分点正是“对智能体互联标准化、平台接入场景分析不足”。现方案的问题定义（小团队故障信息分散、交接难）回答的是“为什么需要 AIOps”，没有回答“为什么必须用 AIP 互联的多个智能体，而不是一个拿着全部工具的单体 Agent”。另外所有智能体同一语言、同一 SDK、同一团队，“异构”目前只体现在业务技术栈上，比较弱。
3. **范围远超工期，且最吃分的平台数据还没开工。** 计划自估 25-38 人日，窗口 10-17 至 10-29，三人满负荷也只有约 36 人日，还没算平台审核和联调的不确定性。与此同时，应用成效（10 分）和附加分第 3 项（4 分）都依赖梧桐后台访问数据，而 AMP 访问日志尚未接入（`platform-missing-fields.json` 中列为 next_development）。

## 三 提升方案

### 1 把创新下沉到官方代码层（创新性 +5~8，技术应用 +2~3）

在 AtomGit / GitHub fork `ACPs-community`，把以下内容实现为 `acps-sdk` 的扩展，并在报告中给出“原生模块 / 改造模块 / 新增模块”对照表和改动行数：

- **AIP 任务接续扩展（原创新二下沉）。** 官方 `aip_group_leader.py` / `aip_group_partner.py` 的任务状态（accepted → working → awaiting-completion → completed）只描述单次交付，没有业务检查点；SDK 里唯一的 resume 是 `aip_stream_server.py` 的流事件续传。在 SDK 层补上：持久任务映射（logical_task ↔ AIP taskId 多次尝试）、协调任期与接管版本 fencing、Partner 中断后经 ADP 重新发现候选并通过 Inbox 邀请入群接续。这是协议级缺口，正好对应评分表“创新设计多智能体协同交互方案，适配 AIP 国标”。
- **AMP 接入与证据通道。** 官方 SDK 已有 `amp/access_emitter.py`、`heartbeat_emitter.py`、`metrics_emitter.py`，但 Partner 基类没有默认接入。做一个 Partner 侧的 AMP 中间件：每个 AIP 任务自动写 access 日志（trace_id 关联 taskId）、心跳、指标、审计。它同时解决三件事：后台访问数据（应用成效 + 附加分）、资源修改审计（交互安全管控）、以及让协调者把“某个 Partner 心跳中断”作为故障证据，直接触发接续。
- **异构协议适配（新增，替代第二业务）。** 写一个 MCP → AIP Partner 适配器：读取任意 MCP server 的工具清单，自动生成 ACS skills，把工具调用包装成 AIP 任务。用它把一个现成的开源 PostgreSQL MCP server 接成数据库方智能体。这样“异构”就成立了：数据库方用的是别人写的现成工具，而不是本队 Python 代码；同时它也是官方通知里明确鼓励的“异构智能体协议适配”方向。截至今天的检索，AIP-PUB 组织下没有找到官方的 ACPs↔MCP 适配项目（名字相近的 ACP-MCP-Server 属于另一套协议），有空间。

原创新一（证据驱动探测排序）保留在应用层，但缩成“模型提出假设与候选探测 + 确定性排序 + 一组消融”，不再追求完整研究级评测。

### 2 重写需求叙事：跨组织、凭据不出域（需求分析 +3）

把核心痛点从“信息分散”改为“**故障处理跨越组织与凭据边界**”：应用团队、DBA 或云数据库厂商、网关或 CDN 提供方各自持有资源和凭据，各自有异构的工具或 Agent。HolmesGPT 这类单体排障 Agent 要求把所有系统的凭据集中给一个进程，跨组织场景不可接受；各方私有 API 之间又没有统一的身份、发现、通信和审计。AIP 恰好提供了这四层（AIC + mTLS、ADP、AIP 群组、AMP），作品验证这套国标能否承载“凭据不出域的跨组织故障协同”，并补上标准缺失的任务接续与异构接入。

这样“为什么必须多智能体互联”“为什么不能单体”都有了正面回答，单智能体对照实验也就有了明确的论点：单体在效果上未必更差，但需要集中全部凭据，这在跨组织场景里是硬约束。需求阶段的调研材料（一段真实故障处理时间线、一次独立部署反馈）保留，提前到本周完成。

### 3 平台数据与访问量提到最前（应用成效 +3~4，附加分 +2）

- 10-18 至 10-20 完成 AMP 接入，并把各智能体部署到一台云 Linux 机器上 7×24 在线，从现在开始积累后台数据。访问排名按相对次数计分，晚一周开始就少一周数据。
- 先在赛题 QQ 群确认三件事：后台“访问量”具体按什么统计（AMP access 日志还是平台转发的任务数）；作品材料中出现平台分配的 AIC 前缀（`1.2.156.3088.1.BUPT...`）是否违反公平性条款（大概率是平台命名空间，但要书面确认）；对官方代码的修改是否要求以 fork 形式提交。
- **访问量要真实。** AMP access 日志由智能体自己上报，伪造很容易，赛方大概率会抽查对照 AIP 任务记录。建议每条 access 日志都关联真实 AIP taskId；靠定时故障演练、持续业务负载产生的真实调用是正当的，纯刷量的自调用循环风险大，不建议。若想获得自然访问，可以额外提供一个只读的公共技能（例如“梧桐接入连通性体检”，供其他队伍检查自己的证书、端点、Inbox 是否正常），本队踩过的坑可以直接变成它的检查项。

### 4 开源贡献与标准化反馈（总结与展望 +3，附加分辅助）

接入过程中已经积累了真实的标准落地问题，例如：CLI 拼 `/acps-adp-v2` 而 Demo 客户端拼 `/discover` 的路径不一致；审核通过后 ADP 一度查不到记录；单 Inbox 需要同时分发邀请与任务反馈；首轮驳回意见与 ACS 字段的对应关系不清。把这些整理成 AIP-PUB 的 Issue，把任务接续、AMP 中间件、MCP 适配器整理成 PR 或独立仓库。这些截图和链接同时是总结与展望高档要求的“对智能体互联标准化落地提出可行、前瞻的优化思路”，以及大纲第五节鼓励的开源贡献佐证，成本很低。

### 5 砍范围

| 原计划内容 | 调整 |
| --- | --- |
| 第二业务 Easy!Appointments（PHP+MySQL） | 删除，由 MCP 适配器接入第三方工具作为复用性证明，更便宜也更贴题 |
| 两台独立节点 | 一台云 Linux（docker compose：Nginx、PostgreSQL、订单应用及资源侧智能体）+ 本地 Windows 协调者，已满足“跨端互联” |
| 17 个故障模板 | 保留 8 个：H00、F01/F02（502 同症异因）、F04 或 F05、F07、F10（复合，主演示）、F12（回复丢失）、F15（成员中断接续） |

## 五 材料层面的提醒

- 作品名称不超过 20 字，例如“凭据不出域的跨组织故障协同智能体”（16 字）。
- 视频必须出现梧桐平台注册、发现、互联、访问全流程和后台访问数据截图，建议录屏中直接打开平台后台页面。
- 所有材料不得出现学校名称、LOGO 和指导教师；提交前全文检索一遍。
- 报告中区分三类数据：平台后台访问量、正式 AIP 任务往返、本地工具调用与历史 425 项本地断言，避免评委误以为混算。
