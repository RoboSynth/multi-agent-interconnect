# 跨系统故障场景与评测设计

本设计围绕订单创建、查询、取消，安排17个故障模板和1个健康对照。故障同时覆盖真实资源异常、相似症状、复合原因、业务结果不明和协作进程中断。每个模板可生成不同参数和部署关系的实例。

[整体架构与业务契约](</D:/AI + 开源/incident-pilot/docs/完整架构与业务设计.md>)定义五类角色：协调者C、应用A、数据库D、基础设施I、业务恢复分析B。协调者参与所有场景。

## 一 业务与实验环境

目标业务由订单应用、PostgreSQL和Nginx构成，具有实际跨节点依赖。业务客户端为每个创建意图生成稳定请求键；订单和创建回执同事务提交。取消使用独立操作键，结果为CREATED变为CANCELLED。

故障注入器单独管理实验环境。真实原因、预期结果和注入时点保存在评测记录中；协调者和参与者只获得业务现象、正常工具结果及允许访问的资源信息。提示、资源名称和日志包装中不写入注入标签。

进程退出由实际进程停止产生；路由错误修改真实网关配置；锁由真实事务产生；只读由数据库设置产生；空间不足使用独立限额数据卷。故障恢复由实际业务读写与资源状态判定。

首轮实验配置如下，正式对照前统一固定：

| 项目 | 初始配置 |
| --- | --- |
| 业务负载 | 每秒1个新创建意图，带后续查询与取消；相同种子生成相同意图 |
| 恢复后观察 | 30秒，至少完成10个新的创建、查询、取消流程 |
| 单事故总时限 | 180秒，包含发现、模型、工具、排队、接续与观察 |
| 资源工具预算 | 全部角色主动诊断、取证、续办和修改合计32次，成功和失败调用都计入 |
| 模型预算 | 合计12次请求、累计输入64k token、累计输出8k token |
| 可用并行度 | 各方法最多3项独立观察并行，同资源修改串行 |
| 发现与通信 | 单独计数，耗时和费用计入总体开销 |

这些数值用于形成可执行的首轮配置，资源试运行后可统一调整；正式比较期间固定。所有方法使用相同参数与预算。

固定负载生成器与观察器的持续业务请求独立计数，不占32次主动工具预算；所有方法共享相同配置。读取观察汇总、按需查询原请求、主动续办等智能体操作计入工具预算。固定负载的结果、模型取证与资源修改分别统计。

## 二 单原因场景

| 编号 | 原因与外部症状 | 关键证据与参与者 | 处理路径 | 业务完成条件 |
| --- | --- | --- | --- | --- |
| H00 | 健康系统，正常创建、查询、取消 | A/D/B提供请求、回执和状态对应 | 正常处理，资源修复动作数为零 | 完整业务流程正常，原有数据保留 |
| F01 | 应用进程退出，网关返回502 | I确认路由目标正确；A确认应用未运行 | 恢复指定应用进程 | 原键请求得到明确结果，新的完整流程正常 |
| F02 | 网关指向旧实例，同样返回502 | I取得实际上游；A证明新实例直达正常 | 恢复已有正确路由版本 | 业务经过公共入口正常完成 |
| F03 | 数据库进程退出，应用依赖失败 | D取得真实进程与连接状态；A提供依赖错误 | 恢复项目数据库进程，应用按需更新连接 | 创建、查询、取消恢复，已有订单可读取 |
| F04 | 应用连接池耗尽，数据库请求超时 | A池内占用及等待高；D可用连接尚足 | 回退池配置或修复明确占用，重建连接状态 | 同负载下恢复，观察窗口内不再次耗尽 |
| F05 | 数据库连接上限耗尽，外部同样超时 | D连接上限与来源；A连接建立失败 | 调整已登记配置，释放本业务已确认废弃连接 | 新连接及完整业务流程正常 |
| F06 | 长事务持锁，读取可能正常而创建或取消超时 | D阻塞链、事务时间和所属业务；A写入等待 | 结束实验业务阻塞事务 | 写入与取消完成，相关请求结果明确 |
| F07 | 数据库会话或角色只读，查询正常而提交失败 | D读写配置；A实际数据库写错误与连接状态 | 恢复读写配置，按需重建应用连接 | 新创建及取消均成功 |
| F08 | 数据卷空间不足，提交失败而部分查询可用 | D写入错误；I限额数据卷用量与可用操作 | 有扩容入口则扩容；无对应能力则转人工 | 自动变体须完成实际提交；人工变体列明所需资源 |
| F09 | 新应用与当前表结构不兼容，旧查询可用而新提交失败 | A部署版本；D迁移版本及缺失字段事实 | 回退已有且兼容当前结构的应用版本 | 使用兼容版本完成完整流程 |

F01与F02构成502同症异因组；F03、F04、F05构成连接或超时同症异因组；F06、F07、F08、F09构成读可用而写失败组。排查策略要通过事实区分原因。

## 三 复合与结果未知场景

| 编号 | 原因与外部症状 | 关键证据与参与者 | 处理路径 | 业务完成条件 |
| --- | --- | --- | --- | --- |
| F10 | 旧网关路由与数据库只读叠加；修好入口后提交仍失败 | I路由；A新实例读写差异；D只读事实 | 修正入口与读写配置，按需更新应用连接 | 两项原因均消除；原请求与新业务流程均有结果 |
| F11 | 应用池耗尽与数据库锁叠加；单独重建连接后仍异常 | A池等待；D阻塞链与连接事实 | 按依赖消除阻塞并恢复连接状态 | 观察窗口内写入持续正常 |
| F12 | 创建已提交，网关丢弃回复；客户端超时 | A提交线索；D原请求键的事务回执和唯一订单；I回复链路 | 查询原回执，以原键返回或续办，恢复回复路径 | 该键只有一张订单，同键重试返回同一订单号 |
| F13 | 请求在到达应用前被阻断；客户端同样超时 | I转发记录；A接收记录；D当前回执情况 | 恢复链路后继续原键请求 | 最终一张订单，原请求后续到达也保持同键 |
| F14 | 取消已提交，回复丢失；客户端不知道是否取消 | D取消回执与订单状态；A请求关联；B用户取消意图 | 读取原取消结果，必要时以原取消键续办 | 订单为CANCELLED，只有一次实际状态变化 |

F12和F13需要不同解释，但共享正确的请求键策略。当前查不到回执，不能直接推出原请求不会稍后提交；后续继续原键。

## 四 成员中断与人工处理场景

| 编号 | 原因与症状 | 中断点与证据 | 处理路径 | 完成条件 |
| --- | --- | --- | --- | --- |
| F15 | 叠加F07只读故障，数据库智能体中断，资源与适配器继续运行 | 三种变体：取证后、修改开始前、修改完成但回报前 | 先做同身份重启；再做有同资源资格的替代AIC接管，读取同一动作记录 | 接续原目标，已完成修改无重复效果，业务恢复 |
| F16 | 协调进程重启，任务推进中断 | 持久事故、任务图、动作编号与各资源当前状态 | 新协调任期读取进展，建立所需新会话，解析在途动作并继续 | 原事故连续关联，资源写无冲突，业务结果明确 |
| F17 | 历史订单丢失且无可用备份 | B原订单凭据；D主库现状及备份事实 | 输出影响范围、已确认事实和人工处理事项 | 正确转人工，不能记为自动恢复 |

## 五 主演示路径

主演示组合F10和F15：业务持续运行时出现旧路由与数据库只读，数据库角色在完成修改后、回报前中断。

| 步骤 | 观众看见的内容 | 系统实际完成的工作 |
| --- | --- | --- |
| 1 | 订单提交由正常变为失败 | 客户端保存原请求键和结果状态 |
| 2 | 发现应用、入口与数据角色，证据逐项到达 | ADP候选、资源能力选择、正式任务与产物 |
| 3 | 初步原因从多项缩小为两项 | 入口旧路由；新应用可读但不可写 |
| 4 | 恢复计划显示动作及依赖 | 修正入口、恢复写入、刷新连接状态 |
| 5 | 数据库成员中断后出现接续者 | 新尝试读取动作记录，确认已经完成的修改 |
| 6 | 原请求得到结果，新订单持续完成 | 创建、查询、取消与数据对应 |
| 7 | 展示业务报告与平台记录 | 端到端耗时、动作、接续、后台访问数据 |

演示视频控制在官方规定的3至5分钟，使用同一实际运行的连续记录和关键画面。F12作为补充案例，单独展示“超时后找到唯一订单”，避免把所有故障塞进同一次演示。

## 六 比较方法与创新归因

冻结v0.2.0只在其原支持场景上作为历史工程参照。正式机制比较使用相同的新业务、工具集合和资源信息。

| 方法 | 行为 | 用于回答的问题 |
| --- | --- | --- |
| 固定顺序流程 | 在同一工具集合内按预设顺序取证与处置 | 自适应是否减少无效检查或遗漏 |
| 同模型单智能体 | 一个智能体可调用相同全部资源工具，自由选择下一步 | 多角色协作相对集中工具调用的收益与开销 |
| 普通多智能体 | 相同角色、工具与预算，自由工具循环，固定参与者 | 显式探测排序与接续机制是否有额外收益 |
| 完整方案 | 探测排序、任务图调整、资源匹配、进展接续 | 整体业务结果 |

创新一采用消融比较：保留相同角色、发现和工具，只移除显式下一探测排序，让模型自由选择。重点使用同症异因和复合组，比较根因判断、探测次数、总体耗时和业务恢复。

创新二分为功能与机制两层。固定成员与重新发现的比较说明替换能力；在相同替代成员和相同中断点下，再比较“从头开始”“转交完整对话”“转交证据进展包”，说明进展表达的作用。三组获得相同资源工具与剩余预算。

接续比较从同一段中断前执行历史分叉，复制协调进展、域内动作记录、业务快照和已采集证据。各组接手同一事实状态，区别仅为交接方式。快照在中断点固定，资源运行时间等会变化的量用相同安排控制。

完整对话超过预算时采用预先固定的截断规则。进展包的生成时间与模型消耗计入本组成本。已发动作及结果未知状态在交接内容中保留，不能将旧动作直接作为新成员的执行清单。

## 七 实验安排

先导比较先选F01/F02、F04/F05两组同症异因，以及F10复合故障、F12/F13结果未知组。用少量配对实例判断机制是否有作用，再扩展故障覆盖。

正式评测在开发开始时按故障模板划分开发变体与保留变体。保留变体改变端口与部署关系、参数、锁来源、错误表现或故障组合，评测前不用于调参。每个选定实例至少重复三次，记录模型波动；开发变体与保留变体分别报告。

每次运行从相同环境快照和业务种子开始，运行次序交错安排。模型版本、系统提示中的通用工具说明、采样参数、上下文与累计预算、可用并行度、工具权限和数据范围固定。单智能体通过同一套适配器获得全部资源工具。

原子幂等与事务回执属于全部方法共享的业务底座。不能把数据库唯一约束带来的零重复订单归因于协作算法；协作比较关注额外探测、处理耗时、资源动作与接续结果。仅靠固定客户端重试即可恢复的实例单列自恢复参照。

两个创新的对照优先在同一梧桐通信条件下进行。额外使用直接工具连接测量通信开销时，单列为工程测量，不能把绕过平台的结果写成官方互联成绩。

F17和F08无扩容能力变体属于预先定义的人工处理场景。报告同时给出全集结局和自动可恢复集合结果。

## 八 指标定义

| 指标 | 定义 |
| --- | --- |
| 根因判断准确率 | 同时定位到实例所要求的原因；复合故障另外报告部分定位 |
| 自动业务恢复率 | 预先定义的自动可恢复实例中，仍有效的原意图达到目标状态且新业务观察通过的比例 |
| 全集结局 | 事故以自动恢复、转人工、自动未完成三种互斥结局列数；未完成另标动作失败、超时或结果未知等原因 |
| 总体耗时 | 收到业务目标至结果与观察完成，包含发现、通信、模型、排队和接续 |
| 诊断耗时 | 收到目标至给出正确且证据充分的原因判断 |
| 探测与动作次数 | 资源观察、资源修改分别计数；失败调用也计入 |
| 重复动作效果 | 同一operation_id产生多次实际资源修改的次数 |
| 业务重复订单 | 同一创建键关联订单数超过一的部分 |
| 已持久受理订单丢失 | 已有持久受理依据却缺失对应订单的数量 |
| 未知请求解决率 | 初始结果未知的意图中，最终得到明确业务结果的比例 |
| 人工参与 | 人工执行或决定的次数与时间 |
| 接续耗时 | 中断发生至原任务重新推进及完成的时间，分别记录 |
| 模型与工具开销 | 累计输入输出、模型调用、资源工具、消息及实际费用 |
| 迁移成本 | 第二业务新增适配器、内核改动、接入用时和支持能力 |

耗时报告中位数和分布；大样本批次再报告p95。健康H00单列零修改表现，不进入故障恢复率分母。请求级即时成功率与意图最终完成率分别呈现，避免重试掩盖服务中断。

每个实例预先定义原意图目标。仍需创建的意图得到相应订单，取消意图得到CANCELLED；未知变为明确失败只说明结果已经解析。事故主动生成完整人工交接事项时记为转人工；运行结束仍未达目标且没有完成交接时记为自动未完成。超时和未知请求数量作为原因与请求级指标单列。

业务原始数据与新产生数据分别评价：未被业务流程修改的原订单保持原值；新增订单与取消状态按用户意图匹配。不能以整个业务库哈希不变作为写入业务的成功条件。

## 九 每次运行保留的产物

每个实例保留环境与版本、业务种子、故障注入记录、实际症状、模型调用、AIP任务与产物、证据引用、动作记录、客户端结果和汇总指标。真实原因只供评测使用。

梧桐后台访问量、官方发现响应、正式任务往返、本地工具调用和业务请求分别记录。后台访问量使用后台数据；本地消息次数用于解释运行过程。
