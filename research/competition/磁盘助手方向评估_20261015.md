# 磁盘助手方向评估与产品方案

2026年10月15日。建议把磁盘助手纳入主候选：围绕“腾出空间，同时保持软件和项目可用”，提供磁盘及文件夹可视化、按用途理解占用、缓存管理，以及依赖感知的软件数据和项目环境迁移。首先面向Windows本机跨磁盘操作，普通用户获得空间分析和常见软件管理，开发、科研和创作用户获得更深入的环境与项目支持。

问题集中且能跨软件复用：用户看到占用，却不清楚目录属于谁、是否仍被使用、删除后的恢复代价，以及移走后原工作能否继续。一个完整产品可以把看占用、看用途、选择方案、执行和验证连起来。扩展应依靠可复用的类型适配和规则，而不是不断加入无关系统优化功能。

**现有工具划出的竞争边界**

| 原始来源 | 已有能力或明确限制 | 对本方案的影响 |
| --- | --- | --- |
| [WinDirStat](https://github.com/windirstat/windirstat) | 磁盘及目录扫描、多种可视化、重复文件、逻辑和实际占用、文件系统监测及清理操作 | 可视化、找大文件和基础清理应视为产品基础 |
| [BleachBit](https://github.com/bleachbit/bleachbit) | 多软件清理规则、预览和清理，开放清理定义 | 不能把缓存识别和预览当作独创 |
| [FreeMove](https://github.com/imDema/FreeMove) | 移动程序目录，通过旧位置的链接继续访问 | “搬目录并留链接”已有直接工具 |
| [disk-cleaner-skill](https://github.com/jcordon5/disk-cleaner-skill) | 对话式分析、风险分类、本地仪表盘、预览及分项授权 | AI解释、风险标签和用户确认已有直接实现 |
| [S.A.K. Utility](https://github.com/RandyNorthrup/S.A.K.-Utility) | Windows工具箱，文档包含迁移、清理及AI辅助工作流 | “Windows上集合迁移、清理和AI”也不是足够的差异 |
| [Python venv](https://docs.python.org/3/library/venv.html) | 环境不被视为可直接移动或复制，应在目标位置重建 | 环境迁移必须按类型选择机制 |
| [Conda-Pack](https://conda.github.io/conda-pack/) | 支持打包环境，并提供前缀修复流程，具有平台及环境限制 | 应利用环境专用工具，并实测目标平台 |
| [Hugging Face缓存文档](https://huggingface.co/docs/huggingface_hub/guides/manage-cache) | 模型缓存包含共享内容和版本引用，已有扫描、删除和预览接口 | “缓存”中可能包含实际工作所需模型，不能按文件夹名直接处理 |
| [微软文件链接说明](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions) | 硬链接限同卷文件；目录junction可跨同机本地卷 | 必须正确区分链接类型、计量和跨盘限制 |

上述能力依据本轮原始文档核查，未在本轮完整运行这些竞品。没有形成“首次”“唯一”或竞争空白结论。

**产品任务和功能**

| 功能 | 用户直接看到或得到什么 | 设计重点 |
| --- | --- | --- |
| 展开磁盘或文件夹 | 目录树、矩形树图、最大占用和筛选结果 | 可从整盘逐层钻取，也能直接指定一个文件夹 |
| 理解目录用途 | 归属软件、项目、环境、缓存、模型、用户资料及依据 | 规则能确定的直接识别，推断与未知单独呈现 |
| 查看空间变化 | 两次快照之间新增、增长、减少的位置 | 回答“最近为什么又满了”，提供持续使用价值 |
| 管理缓存 | 具体候选、可回收估算、再生成或下载成本 | 优先利用软件自身管理方式，保留当前必要版本和已知依赖 |
| 搬迁数据与环境 | 相关目录、已知依赖、迁移方式及可验证的方案 | 迁移对象可以跨多个位置，不仅是当前选中的文件夹 |
| 操作与结果记录 | 实际变更、实际空间变化、功能检查和恢复入口 | 明确区分已发现、已计划、已执行、已验证和未完成 |

空间信息至少区分文件逻辑大小、文件实际分配、所选操作预计释放量和执行后卷空闲变化。硬链接、共享缓存、压缩文件和目录链接都会影响计量；不能把目录累计大小直接宣传为可释放空间。无法访问的部分应标记为未统计，不报告整盘完全扫描成功。

界面建议采用左侧磁盘与目录导航、中间交互占用图、右侧用途和依据、底部操作队列。点击大目录后，用户可以继续展开、查看归属、制定缓存处理或迁移方案，再查看结果。聊天用于解释与提出目标，不替代主要操作入口。

**迁移应按对象选择方法**

产品中的“安全搬家”应有具体含义：在已声明支持的类型和条件下，检查已知依赖，按适用机制执行，并以原任务检查结果判断是否成功。任意软件依赖完全自动发现、任意程序随意搬动，不能作为第一版承诺。

| 类型 | 候选迁移方式 | 迁移后需要检查什么 |
| --- | --- | --- |
| 普通资料、可独立搬动的项目 | 复制完整文件及已识别外部资源，更新受支持的引用 | 打开项目，执行用户原本需要的读写或导出 |
| 提供数据位置配置的软件 | 使用软件自身设置、配置项或正式迁移入口 | 软件读到新位置，并能继续保存和重启 |
| 条件适用的应用数据目录 | 搬到目标卷，在原位置保留目录junction | 旧路径可访问、权限正确、重启后的实际任务通过 |
| Python venv项目 | 在目标位置重建兼容环境，处理项目内可编辑依赖 | 指定解释器、关键导入和原任务产物 |
| Conda环境 | 根据平台、安装方式和限制选择克隆、重建或Conda-Pack | 原任务、路径前缀、项目和数据引用 |
| 模型及包管理缓存 | 用管理器识别引用和布局，按支持的配置迁移缓存根目录 | 已选模型可加载，已知项目可继续运行 |
| 含服务或特殊安装机制的软件 | 采用已验证的软件专用适配和正式管理流程 | 相关服务及用户任务恢复；条件不明则仅给出调查结果 |

保留旧路径链接适用于同机跨盘的一部分情况，它并没有消除软件内部所有依赖，也不代表可以跨电脑使用。目标环境的重建同样不能仅靠一份宽松包列表保证完全一致，必须验证实际工作。

一项迁移的可检查流程是：采集源状态和已知关联；确定目标容量、迁移方式和验收任务；复制并核对；在源内容稳定后完成最终同步；切换路径或配置；重跑验收；保留恢复所需信息并报告空间变化。文件仍在持续写入时，应先解决稳定性，不能把一次哈希通过当成最终一致。

“程序能启动”只是一个检查层级。项目迁移至少运行原来的处理、构建或导出任务；模型迁移至少实际加载所选版本；应用数据迁移至少读取、保存并在重启后复验。迁移执行器不以模型的完成声明作为成功依据。

**缓存处理和恢复的边界**

缓存可以按恢复成本分为临时内容、可重建内容、需重新下载的资源，以及用途不明或涉及用户状态的内容。可重建不等于没有代价：离线模型、包缓存和构建缓存，可能直接影响下一次工作。

删除候选应结合软件规则、管理器引用、已知项目、当前使用证据和用户选择。最近访问时间只是一条线索；“没发现引用”也不能自动等同于“没有依赖”。应显示证据来源和覆盖范围。

每种操作需要标明恢复方式：保留副本的迁移可按日志回切；经测试可重建的缓存可以重建；下载资源恢复依赖来源仍可访问；未保留副本的永久删除不能承诺一键撤销。

容量统计必须与恢复策略一致：把文件送入同卷回收站通常不会释放相应的卷空间；迁移后若源卷仍保留完整旧副本，也不能提前把那部分容量算作已释放。实际空闲变化应在可解释的条件下测量，同时记录其他进程写入造成的干扰。

**AI和程序分别负责什么**

AI适合帮助理解陌生目录和项目说明、汇总分散配置、解释已知依赖、把用户目标转成候选方案，以及在结果异常时调整调查步骤。例如用户提出“给C盘腾一些空间，优先搬走可以迁移的数据，并保留当前工作环境”，AI可以综合多个候选的收益、恢复成本和依赖约束。

空间扫描、内容计量、权限和链接检查、复制、校验、软件专用操作、功能探针及日志由确定性程序完成。AI输出受约束的结构化方案，执行器检查具体目标和动作。路径名或模型判断不能直接变成不受限制的删除命令。

目录归属先利用确定性规则识别：软件已知目录、项目清单、环境元数据、缓存索引及配置引用。AI补充处理无法完全规则化的含义与关联，并给出依据和待确认项。若纯规则方案已经同样好用，AI部分就需要重新寻找实质作用。

**最值得验证的自研贡献**

第一，建立带证据的空间归属与依赖表示。把文件或目录归入软件、环境、项目和共享资源，记录关系来自配置、管理器索引、运行探针还是语义推断，并保留未知。用户看见的是“这一组资源为什么关联”，而不仅是文件路径列表。

第二，根据用户保留条件联合选择清理和迁移方案。在空间目标、目标盘容量、重新下载代价、已知依赖和允许修改范围下，提出方案并解释取舍；比较是否比按大小或固定规则排序减少用户决策劳动。单纯换一种图表不足以支撑这项贡献。

第三，用对象专用的迁移配方和原任务验收，降低目录层面成功、实际工作失败的比例。每个配方包括识别条件、依赖探针、执行方式、验收和恢复信息。预览、备份、日志和用户确认本身已有实现，贡献应以跨对象和跨项目的实际收益证明。

上述都是候选方法，需要进一步专项检索和对照，不能直接称为首创。若只是把现有分析器、清理器和搬迁工具接入聊天界面，自研差异仍然薄弱。

**建议的首个完整版本**

先完成Windows桌面端一个贯通流程：选择盘或文件夹，展开占用；识别常见软件及项目类型；选择清理或迁移对象；显示依据和计划；执行受支持操作；检验空间和原任务结果。通用功能服务普通用户，较复杂的项目环境搬迁作为深入能力。

首批可选择普通项目目录、可配置数据位置的应用、Python项目环境，以及一类带共享引用的模型缓存。具体软件和版本应通过预实验决定。清理规则可以先覆盖少量实际高频类型；每新增一种环境类型，都配套识别、执行、验收和恢复记录。

扩展成果包括：依赖关系表示、应用适配接口、可验证的迁移配方、缓存处理规则，以及在隔离环境中可重跑的故障与恢复任务集。它们进入产品核心流程，才有明确开源复用价值。WinDirStat、BleachBit和FreeMove的许可条件应结合实际复用方式核对，不能假定所有组件都采用宽松许可。

**验证设计与立项判断**

可先构造24个可重跑任务，分别覆盖占用解释、缓存处理、数据或环境迁移、异常及恢复，每类6个。数量是验证建议。使用隔离虚拟机或可丢弃的测试卷，以及自行准备或依法可复现的项目；随后补充实际用户任务。

对照至少包含现有工具组合、同模型的通用Agent、纯规则版本和完整系统。固定任务及允许修改范围，把人工检查、配置、等待和恢复都计入成本；记录未支持和拒绝处理的对象。

主要指标是：已知类型的归属与依赖判断正确性；可回收量估算偏差；空间目标达成；迁移后的原任务成功率；虚报成功；必要数据误删或错误变更；中断后的可恢复性；用户总操作时间，以及重新下载和重建代价。

至少包含这些失败条件：源正在变化、目标空间不足、权限不足、已有同名目录、跨盘链接、共享缓存、配置中的旧绝对路径、操作中断和验收不通过。统计成功案例之外，也要记录哪些信息不足以形成可靠方案。

推荐进入主候选的理由是任务真实、覆盖广、结果直观，并有环境和项目依赖这一深入点。正式立项的门槛是：在相同的保留条件下，用户更容易选出方案并完成操作；原任务可用性优于简单搬目录或通用Agent；AI或自研方法至少有一项独立收益；第三方能通过适配接口扩展新软件。

当前完成的是资料核查和产品方案。本轮未扫描用户其他磁盘目录，未执行清理或迁移，也未产生产品运行数据。
