## 选题判断

官方评分中，实现与可验证效果25分、AI与开源融合20分、开放成果与复用15分，合计60分；创新设计20分。适合本队的路线是围绕开源开发中的具体任务，做一个可执行、能独立复验的工具，并把团队新增机制与原有组件分开说明。评分权重见同目录《参赛要求与评分速查》及官网附件。[规则入口](https://www.aicomp.cn/tracks/tracks-5/4924.html)

## 首选方案

建议作品名称：开源补丁需求覆盖验收助手。

建议申报方向：AI开发工具与开源协作。如果后续主要成果成为某一上游工具的实质扩展，也可以按开源项目改进方向重新判断。

### 用户和问题

目标用户是审核AI生成补丁的开源维护者。一个Issue可能同时要求正常输入、边界输入和错误处理都正确，而候选补丁只解决其中一部分。工具需要告诉维护者：哪些要求已获得证据，哪些被反例推翻，哪些仍无法确认。

演示示例为自拟需求：字符串配置转换器需支持前后空格、接受合法布尔值、拒绝非法值。候选补丁通过了正常值测试，却把非法值静默解释为false。系统展示遗漏的要求、对应输入、实际输出、期望依据及可直接运行的复现测试。这个例子说明产品形态，不能作为真实开源案例数量。

### 最小可交付范围

输入为固定版本的Python仓库、Issue文本、候选补丁及用户确认的需求清单。输出为逐项验收报告、可运行测试、失败记录和可下载证据包。

只支持有本地CPU测试的小型Python库，优先文本处理、配置解析、序列化和参数校验。先提供本地命令和简单结果页；用户能导入Agent生成的补丁即可。自动生成修复建议可作为扩展，不把整套自动修复平台作为首版依赖。

首版不承担任意语言、任意仓库、复杂数据库或浏览器服务的自动适配。用环境模板支持经筛选的仓库，并明确哪些情况尚不支持。程序修改必须在受限的独立工作副本内进行；评测标准和答案不能放在被测Agent能够访问的位置。

### 可验证的改进假设

| 拟实现机制 | 自研内容 | 验证问题 |
| --- | --- | --- |
| 需求到测试的覆盖映射 | 将Issue拆成可确认行为，为每条行为保存原文依据、测试、运行结果和未覆盖原因 | 能否比普通Agent审查少漏掉部分修复？ |
| 面向遗漏要求的测试分配 | 根据尚无证据的要求、修改位置和预算选择下一项验证 | 在相同调用和时间预算下，是否发现更多遗漏？ |
| 证据充分性控制 | 测试需区分预期修复与错误行为；证据绑定代码版本；无法判断时保留不确定状态 | 能否减少无效测试造成的错误通过，同时避免大量拒绝正确补丁？ |

这些是需要实现和实测的候选贡献。需求覆盖、差分测试、补丁验证和预算分配都不是可直接宣称首次提出的概念。应把创新表述落在具体机制、适用场景和相对基线的改善上；仅添加清单界面或把提示词拆给多个Agent，贡献不足。

AI负责理解Issue、寻找相关代码、构造测试候选及解释失败；测试框架和运行器提供实际执行证据。需求歧义由用户确认，最终通过也只表示当前验收范围内有证据支持，不代表证明整个程序无缺陷。

### 已有工作和区别

| 原始来源 | 已经覆盖的能力 | 对本项目的约束 |
| --- | --- | --- |
| [SWE-agent](https://github.com/SWE-agent/SWE-agent) | 从GitHub Issue尝试完成代码修复；README现推荐后续mini-swe-agent | 自动修复本身不构成差异 |
| [Agentless](https://github.com/OpenAutoCoder/Agentless) | 开源软件修复流程及补丁选择；相关流程含复现与回归测试 | 不能把补丁后运行测试当作新方法 |
| [SWT-Bench](https://github.com/logic-star-ai/swt-bench) | 用原始错误状态与修复状态评价Issue复现测试 | 仅生成一个先失败后成功的测试已有公开基准 |
| [CounterPatch](https://github.com/kirilkirkov/counterpatch) | 作者描述了补丁前后差分执行、反例缩减和pytest复现 | 反例生成不是空白；需比较需求遗漏处理等具体差异 |
| [PatchProof](https://github.com/taneemishere/patchproof) | 作者描述了多项检查、证据记录及有界修复搜索 | 证据记录或设置检查门槛本身不足以宣称创新 |

本次核查了项目说明和公开论文/基准介绍，没有运行这些工具，也未完成逐模块源代码审计。不能把README的功能声明当作实测效果，或宣称它们绝对没有某个功能。立项时应固定最接近项目的版本并实际比较。

## 怎样形成可信结果

目标规模是收集30个基础Issue，其中10个用于开发、20个作为保留测试集，覆盖至少3个可运行的开源仓库。先做5个Issue的小试验，再按环境准备速度调整。若只能可靠复现更少案例，应缩小结论，不能用大量同质变体充作独立案例。

每个Issue至少准备正确修复、部分修复和引入相关回归三种候选补丁。自然产生的Agent补丁与人工构造缺陷分开统计；一个Issue的所有变体必须进入同一数据划分。历史修复可能已被模型训练见过，因此主要检验固定候选补丁的验收能力，不宣称零污染泛化成绩。

候选补丁和验收标准需由两名队员交叉核验。所有比较方法可看到同样的公开需求；保留评分测试及参考补丁不可供被测Agent读取。测试生成与最终评分不能由同一个可修改的脚本自证。原始代码与参考修复都应能在固定环境重现预期状态。

### 对照和消融

1. 仓库现有测试：衡量没有额外AI验收时能发现什么。
2. 强单Agent验收：给同样需求、代码、执行工具与预算，明确要求覆盖全部需求并主动找反例；不能故意使用弱提示。
3. 最接近的开源工具：从上述项目中选支持相同任务的工具，记录版本、配置和不支持的范围。
4. 本方案：相同模型和预算，显式维护逐项证据及遗漏优先级。
5. 消融：移除遗漏优先级或证据有效性检查，检验新增机制是否有独立作用。

部署失败与验收错误分开计数；选定案例后不能悄悄排除不利结果。若同类工具暂时无法运行，只能报告功能比较和原因，不宣称性能超过它。

### 指标

| 指标 | 含义 |
| --- | --- |
| 错误通过率 | 错误补丁中被系统判为通过的比例 |
| 正确通过率 | 正确补丁中被系统放行的比例 |
| 不确定率 | 系统未能作出有证据结论的比例，按正确/错误补丁分别报告 |
| 需求遗漏发现率 | 独立标注的遗漏行为中被发现的比例 |
| 复现有效率 | 给出的失败测试经独立重放确实有效的比例 |
| 耗时和用量 | 每任务墙钟时间、调用次数、可得的token用量及超时数 |

同时报告错误通过和正确通过，防止靠全部拒绝制造好成绩。展示配对结果和逐Issue记录，小样本结论应限于测试集，不外推成生产可靠性承诺。正式报告优先采用固定预算下的对比，并记录模型、工具、环境版本；拿不到token数据时写未知，不写零。

产品中的测试选择不能访问保留评分测试。文件哈希和结果追溯属于工程完整性，不能独立当成算法创新。

## 备选方案

建议作品名称：开源文档示例跨版本修复助手。

用户提供一个Python项目的旧版、新版及文档示例。系统定位因API变化失效的示例，生成修改，在新版本执行，并检查示例原有教学目标是否保留。只处理Markdown中的可执行Python示例，首版排除大型Notebook、外部云服务和GPU训练示例。

现有[pydantic/pytest-examples](https://github.com/pydantic/pytest-examples)已经支持运行文档代码和检查打印结果；[Evidoc](https://github.com/handong66/Evidoc)已经描述了路径、命令、API等文档漂移检查以及修复工作流。因此“文档能运行”或“文档与代码保持同步”不能作为首次创新。

可研究的收窄点是：旧版本成功、新版本失败的同一个例子，怎样在修复后仍保留原任务。比如示例本来教异常处理，删除抛错代码虽让脚本通过却失去意义。团队需把示例目标变成独立可验证的断言，评价运行修复率和语义保持率，而不是仅统计不报错比例。

两天可行性目标：找到至少2个项目、5个有清晰版本变化的真实示例，完成双版本重放和至少一个修复。正式目标为3—5个项目、20—30个案例，取决于实际可用样本。基线包括现有运行检查器、直接让Agent修报错、加入目标约束的方案。开放示例集、版本清单、测试脚本和修复工具。

这一方向工程风险较低，演示效果直接；主要风险是可用样本不足和语义目标依赖人工。它也必须先验证，不能当作不需要创新证据的保底项目。

## 第三候选的适用条件

单一SDK升级迁移助手仅在队伍熟悉某个库、能取得真实下游项目时考虑。[LibCST](https://github.com/Instagram/LibCST)提供Python代码结构转换基础，[Griffe](https://github.com/mkdocstrings/griffe)用于提取API结构和识别破坏性变化。基于它们做语义迁移和执行验证可能有价值，但仅用AI替换函数名没有充分区别。

首版只选一个库的一次明确版本迁移，检验跨文件调用修改后原有行为是否保持。没有稳定历史样本就不选，避免把赛期花在筛库和搭环境上。

## 两天立项检查

以下是团队自定的进度检查，不是赛事规则。

| 时间 | 任务 | 立项证据 |
| --- | --- | --- |
| 第一天上午 | 固定范围、确认运行环境和实际Agent吞吐 | CPU测试可运行；有统一结果格式 |
| 第一天下午 | 收集并重放候选Issue | 至少5个来自真实项目的案例，需求和状态可解释 |
| 第二天上午 | 实现最小验收流程并跑强单Agent对照 | 能给出可重放的具体遗漏，而非只有自然语言结论 |
| 第二天下午 | 交叉复核、比较最接近工具、决定范围 | 至少出现值得继续验证的差异；明确最大误报与数据缺口 |

继续首选的条件：案例可获得、工程链路能闭合、新增机制有可解释的潜在价值。两天观察不用于宣称显著效果。若目标需求仍需大量临时人工补写、基线已解决同样问题、或环境准备持续失控，应缩小到某类错误，或改选经过小试验的文档方向。

## 对应评分项的交付证据

| 分值 | 作品需要提供的证据 |
| --- | --- |
| 场景15 | 真实Issue、维护工作流程、开发者试用反馈 |
| 创新20 | 明确机制、强基线、最接近工具比较、消融和失败边界 |
| AI与开源20 | AI参与的必要环节、上游组件、自研模块、资源与许可证清单 |
| 完成度25 | 可运行工具、独立复验、原始结果、失败记录 |
| 开放复用15 | 代码、案例元数据、合法可发布的测试、环境和使用文档、维护计划 |
| 表达5 | 报告与演示围绕同一真实案例，清楚区分已有能力和新增贡献 |

开放数据和代码要核查上游许可与再分发条件。向上游提Issue或PR可以提供贡献证据，但不把“上游必须及时合并”作为交付依赖，也不把发PR本身等同于贡献有效。

最有说服力的答辩应能现场重现：一个真实问题、常规方式为什么漏检、你们增加的机制如何发现、怎样复验，以及在哪些场景还会失败。优先完成这些证据，再做视觉和功能扩展。
