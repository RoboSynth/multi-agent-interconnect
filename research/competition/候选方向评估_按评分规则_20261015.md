## 三、四个推荐方向

### 方向A：实验账本——把散乱的实验文件夹整理成可复现的对比表

**谁、什么时候卡住。** 做机器学习或计算实验的学生，跑了几十次实验，配置改来改去，结果散在日志、notebook、终端输出和截图里。写论文或组会汇报时才发现："效果最好的那次，到底用的什么参数？"只能翻文件夹、对时间戳，有时根本找不回来。

**做什么。** 指定一个实验文件夹，工具读取配置文件、训练日志、指标文件、notebook 和输出目录，重建"哪个配置对应哪个结果"的对比表。每个数字都链接到出处文件和行号；对应不上的标"不确定"，不硬猜。用户可以点"复跑验证"，用重建出的配置重新跑一次，确认结果能复现。整理后的记录可以导出到 MLflow，之后接着用正规工具管理。

**竞品情况。** MLflow、W&B、Aim、ClearML 都要求做实验时就接入，事后导入只支持 TensorBoard 文件等少数格式，未发现能从杂乱文件中用 AI 重建记录的工具。

两篇2026年的相关研究可作为设计依据，但它们研究的不是实验文件夹整理本身，引用时要说清楚。第一篇让大模型从智能体运行日志中重建"哪条记录支撑哪个结论"，在28个缺少关键对应信息的案例中，模型有26个给出了没有证据支撑的出处断言，其中22个答案碰巧正确（[arXiv 2610.09581](https://arxiv.org/abs/2610.09581)）。这说明"答案对"不等于"有出处"，需要显式保留证据链接。第二篇评测 Agent 复现 NeurIPS 论文结果，最好的 Agent 在代码、数据和权重齐全时也只复现了41%，最常见的错误是不对照论文数字做检查（[RECLAIM](https://arxiv.org/abs/2609.28850)），说明机器学习结果的可复现性本身就是难题。"每个数字都有出处、标出不确定、可复跑验证"正是据此设计的。

**为什么不空泛、不过垂直。** 输入是一个文件夹，输出是一张带出处的表，范围非常明确。用户覆盖机器学习、计算模拟和数据分析方向的大量本科生和研究生，在 AI 赛道里，评委本人或他们的学生多半就是这类用户。

**AI 与开源。** 文件格式五花八门，参数在文件名、命令行、配置文件和代码里各写一半，必须靠 AI 理解和对齐；数值提取、出处链接和复跑交给确定性程序。兼容 MLflow 等开源生态，可以把导入器贡献给上游。

**如何证明效果。** 两类数据。一类是人工构造的、已知正确答案的混乱文件夹，用于测准确率。另一类是向同学收集的真实实验文件夹，由当事人核对结果。指标包括对应准确率、虚构出处次数、"不确定"标注的准确性，并与"把文件夹直接交给通用 Agent"作对比。

**演示。** 打开一个真实的、很乱的实验文件夹，30秒后生成对比表；点击最佳结果，跳转到出处文件；点击"复跑验证"，结果一致。

**风险。** 真实文件夹差异极大，首版限定 PyTorch 和常见日志格式；复跑需要时间，演示时选短实验。

### 方向B：MATLAB 代码迁移到 Python，并验证结果一致

**谁、什么时候卡住。** 理工科学生和科研人员手里有大量 MATLAB 代码，包括课程作业、老师留下的程序和数学建模比赛代码。想换到免费的 Python 生态的原因很多：毕业后没有学校授权、实验室没钱买工具箱、想用 Python 的深度学习库。2020年 MathWorks 对哈工大、哈工程停止授权，这件事让很多高校意识到依赖风险。现在的困难是：AI 能大致翻译代码，但翻译完不知道对不对，数值上的细小差异（下标从1还是0开始、矩阵按行还是按列存储、默认参数不同）很难人工核查。

**做什么。** 输入 MATLAB 脚本或函数，AI 翻译成 Python（NumPy、SciPy、Matplotlib）。用开源的 GNU Octave 运行原代码作为参照，自动比对两边每个关键变量的数值和生成的图像；不一致就定位到具体变量和行，交给 AI 修正，直到一致或明确报告无法迁移的部分（例如 Octave 不支持的工具箱函数）。

**竞品情况。** SMOP、matlab2python 等规则工具已停更多年；在线 AI 转换工具只翻译、不验证。最接近的是2026年8月的 r2py 论文，它把 R 包迁移到 Python 并做数值比对（[arXiv 2608.16911](https://arxiv.org/abs/2608.16911)），证明这条路可行，但针对的是 R 语言。未发现针对 MATLAB、以 Octave 作参照的开源验证闭环工具。

**为什么不空泛、不过垂直。** 只做一种语言迁移，范围清楚；MATLAB 在国内理工科和数学建模中用户量很大。

**AI 与开源。** 代码翻译和根据差异修正必须靠 AI；Octave、NumPy 和 SciPy 全是开源组件，"把代码从商业软件迁移到开源生态"本身就是开源生态价值。

**如何证明效果。** 用公开授权的 MATLAB 代码（GitHub 上的开源 MATLAB 项目、课程示例）组成测试集，对比"只让 AI 翻译"与"翻译加验证修正"两组：数值一致率、需要人工修改的行数、隐蔽错误数（能运行但结果不对）。

**演示。** 拖入一份数学建模的 MATLAB 代码，左边 Octave 结果，右边 Python 结果；第一次翻译有一处下标错误，工具自动定位并修正，最终逐变量一致，两张图重合。

**风险。** 国内不少人在用盗版 MATLAB，迁移的紧迫感比预想的弱，场景价值需要用问卷数据支撑；Octave 和 MATLAB 本身存在少量不一致，需要如实说明。

### 方向C：开源文档示例执行验证与修复

**谁、什么时候卡住。** 开源项目的使用者照着 README 和文档里的示例敲代码，结果因为版本更新早就跑不通了；维护者没有精力逐条检查文档。

**做什么。** 自动执行一个开源项目文档中的全部安装命令和代码示例，找出失效的条目，结合版本变更日志定位原因，生成修复并再次执行验证，最后整理成给原项目的 PR。

**竞品情况。** Doc Detective、Runme、mktestdocs 只检测不修复；Mintlify、Swimm、Promptless 等商业工具根据代码变化让大模型改写文档，但不执行验证。未发现"执行 → 定位 → 修复 → 再执行 → PR"的完整闭环。不过用 GitHub 的 Agent 工作流拼出类似流程并不难，壁垒需要靠验证质量和评测数据建立。

**优势。** 开源生态价值和社区贡献证据最硬：给真实项目提交的修复 PR 本身就是成果。能复用 error-assistant 已有的"运行、验收、回退"代码。

**弱点。** 用户主要是开发者和维护者，场景价值的说服力不如 A、B 直观；PR 是否被合并要等维护者。

### 方向D：本地开源模型选型实测

**谁、什么时候卡住。** 想在自己电脑上用开源 AI 做语音转文字、文字识别或文档检索的学生和开发者，面对几十个开源模型不知道选哪个，也不知道自己的电脑能不能跑、跑在自己的数据上效果如何。

**做什么。** 用户选择任务，放入几份自己的样例数据，工具根据电脑配置挑出候选开源模型，在本机下载运行，计算语音识别错字率、文字识别准确率、检索命中率等指标，同时记录速度和显存，给出推荐。

**竞品情况。** llmfit（约3.8万星）、CanIRun.ai 等只针对大语言模型，且只测速度或估算能否运行；lm-evaluation-harness、OpenCompass 面向研究者。未发现面向普通用户、覆盖非大语言模型任务、用自有数据测质量的工具。

**弱点。** 要支持多个任务的多个模型，下载和运行环境的工程量大，国内下载慢，15天风险最高；AI 的作用主要体现在被测对象上，评委可能追问工具本身的 AI 作用。

## 五、推荐

**首选 A：实验账本。** 四个方向中，它在"真实问题"和"竞品空白"两点上最强：做过实验的人几乎都遇到过这个痛点，又未发现同类工具；2026年的相关研究表明大模型在重建日志来源时容易给出没有证据的出处，"每个数字有出处、可复跑"的设计因此有依据。用户自带 API 也很自然，实验代码和数据属于研究者，不应上传第三方。

**次选 B：MATLAB 迁移验证。** 对错最客观，演示效果最直观，开源生态的叙事也最顺。需要先做一份小问卷，确认同学们迁移的意愿。

**C 适合作为补充或备选。** 它和现有 error-assistant 代码衔接最好，社区贡献证据最硬。

**D 暂不推荐作为初赛主线**，工期风险太大。

## 六、下一步建议

在10月16日内完成以下两件事，再最终定题：

1. 团队三人各找一个自己或同学的真实实验文件夹（方向A），或一份真实的 MATLAB 代码（方向B），拿通用大模型手工试一次。看问题是否真实存在、AI 能做到几成，这一步只需要半天。
2. 向10名同学发一个两题小问卷：是否遇到过找不到最佳实验配置的情况；是否有迁移 MATLAB 代码的需求。结果直接写进报告的需求论证部分。
