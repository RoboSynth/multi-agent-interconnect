# V3 / V4 现场采集运行提要

本提要由当前源码和 10-20 批次的参数生成脚本只读核对形成。源码参考提交：`c88b203ff417dca0b028784a569e741d62db2c02`，使用当前工作树。未启动云端任务、未修改代码、未复制历史结果。下列源码路径均相对于当前团队仓库；真实身份、地址、证书、密钥仅由私有配置引用。

## 先解决的采集缺口

1. 10-20 F10 使用 M0 和自动审批。当前 `eval/run.py:251` 自动处理 pending 审批，`--approve-high` 为真时直接批准，每 0.1 秒轮询；这条路径没有“弹窗停留两秒再点击”。保持同方法同参数时，审批只能如实展示为预授权。手动审批演示必须单独标注，不能伪装为原评测参数。
2. 现有工作台不是独立评测进程的只读查看器。`workbench_server.py:58` 会启动自己的 transport，`:76` 建立自己的 engine，`:132` 从其内存取状态。另开同配置工作台会增加消费者；把输出目录设成相同目录也不能同步这两个 engine。
3. 租约交接时，`ops/longrun_host.py:255` 令当前 Uvicorn 服务退出，关闭消费者后才在 `:271` 标记 paused。因此交出身份后，原 8877 页面不能直接承担此次评测的直播。要满足“同次运行+真实工作台”，需将展示绑定到唯一执行引擎，或增设仅读取本次事件的展示通道；当前源码未提供该适配，本提要不声称已就绪。
4. `incident/wutong_transport.py:63` 的 `record()` 不自动给原始 `events.jsonl` 加时间；`eval/observation.py:68` 使用 `at_monotonic`。采集需在现场记录 UTC/monotonic 对应锚点和录像起点，保留有原生时间戳的日志；缺少发生时间的事件标为未知或注明“采集到达时间”，不能按行号、文件时间推算。

## 租约暂停与恢复语义

`eval/leased_batch.py` 是 Python API，没有独立 CLI。必须与当前长期主管共用七个身份、control directory 和 lease directory，配置值由主管的私有设置引用。

1. `ops/aic_lease.py:154` 检查主管 running 且身份集合完全一致，发出绑定 host_session/request_id 的 stop_when_idle 请求。
2. 主管进入 draining，拒绝新事故；已有任务空闲后正常关闭工作台与消费者、释放租约，写 paused 确认（`ops/longrun_host.py:219`、`:255`）。请求方不会强杀原消费者。
3. 请求方确认 consumers_closed 和 lease_released，再取得全部本机 OS 文件锁（`ops/aic_lease.py:173`）。默认交接超时 180 秒；10-20 批次显式使用 840 秒（历史 cloud_batch `:375`）。本机锁不能证明另一台机器没有相同身份消费者。
4. 每个已尝试案例都必须确认资源复原、独立 H00、消费者关闭、正常关组，无未尝试/隔离案例，才接受清理回执（`eval/platform_batch.py:28`，`eval/leased_batch.py:19`）。案例本身失败但清理完整，可以保留失败后恢复巡检；清理未知则隔离身份。
5. 回执完整才写 action=resume；缺少回执写 quarantine；尚未取得租约的取消写 cancel（`ops/aic_lease.py:194`）。采集保存 planned_pause_requested / started / finished 的真实记录（`ops/longrun_host.py:253`、`:272`、`:233`），不能把“准备恢复”写成“已恢复”。

## SSH 恢复后的最小真实执行路径

只安排两例：`F10/M0/seed101/repeat1` → `E1-a/after_applied/repeat1`，不附带另外两个中断点。

1. **读取当前部署**：在云端只读核对 checkout/源码、镜像 digest、target 的项目/端口、七身份配置引用、主管 host.json 的 session/status/control/lease 目录，以及当前事故和未知在途操作。用当下配置生成新计划；不使用 10-20 已消费的计划、授权或结果目录。
2. **离线准备两例**：F10 参数按上表绑定；E1-a 以当前实验 bundle 调用 `eval.platform_resume_experiment.prepare()` 冻结新 plan，`validate_plan()` 校验。输出使用新的 `eval/results/platform/video-<batch>/` 子目录。两例包装器需要明确校验两条计划；已有 cloud_batch 的四例 validate 不能原封不动用于两例。
3. **先就绪采集**：独立只读展示端必须只消费本次新输出，不启动 `WutongTransport`。准备录像/actions 记录、UTC/monotonic 锚点、双方 AMP 日志增量边界和审批脱敏投影；不能把原 8877 工作台启动为第二协调者。展示适配由单独采集组件处理。
4. **统一租约执行**：调用 `run_leased_batch()`，两例 `run_case` 回调分别采用 F10 的 `eval.run.run()` 加正常关组/复原/H00 包装，和 E1-a 的 `authorize()` + `run_case()`。每例先确认旧六域消费者已关闭，再按当前绑定 compose 启动该例拥有的六域消费者；记录容器身份和镜像，最终只正常关闭本例拥有的消费者并合并清理回执。相关现成职责可对照 10-20 helper 的 `f10_case`（`:295`）及 `run_case`（`:318`）；它们可作为适配依据，不执行旧四例 launcher。
5. **逐例保留结果并恢复**：F10 完成清理后才进入 E1-a；任何清理不明由 `run_leased_batch` 留存失败并隔离。结束后读取真实 `planned_pause_finished` 和 host running 状态再记录巡检恢复。最后从这两例新目录匿名导出 V3/V4 素材，校验录像/事件共享批次和时钟锚点。

当前结论：以上是最小执行接线与现有函数路径；两例包装器、单消费者只读 UI 和同步采集接线尚未在本轮生成或运行。SSH 恢复后先补齐这些接线，再执行真实案例，不能把本提要当作可直接运行脚本或成功证据。
